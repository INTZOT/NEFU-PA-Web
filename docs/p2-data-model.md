## 二、实体与字段

### 1. User · 用户

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | 标识 | |
| name | 文本 | **真实姓名** —— 成员之间可见（R-53），排行榜展示（R-54） |
| student_id | 文本（10 位数字） | **登录标识**；格式校验，**不校验真伪**（D-06）；**不对任何人展示** |
| qq_number | 文本 | **登录标识 + 绑定凭据 + 密码重置核验依据**（D-13、D-15） |
| password | 凭据 | 经 QQ 聊天通道设置（D-15） |
| self_rating | 数值 0–1000 | **个人自评分**；不随比赛变化；可随时自行修改（D-22、D-24） |
| role | 枚举 | member / admin / super_admin（D-16、D-23） |
| created_at | 时间 | 注册时间 |

> **注意**：这里**没有**"本赛季比赛积分"字段 —— 比赛积分存放在 SeasonRating 中，因为它是**按赛季分段**的（D-25）。

### 3. SeasonRating · 赛季积分

**每（用户 × 赛季）一条。** 这是"比赛积分"的实际存放处。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | 标识 | |
| user_id | 引用 → User | |
| season_id | 引用 → Season | |
| rating | 数值 | **比赛积分**，初始 **500**（D-09） |
| wins / losses | 整数 | 战绩（仅官方比赛，R-70） |
| matches | 整数 | 场次 = wins + losses（可派生，冗余存储便于排序） |

**唯一约束**：`(user_id, season_id)` 唯一。

**赛季归档的实现**：归档**不修改任何积分数据** —— 只是把 Season.status 置为 archived，同时创建新赛季。新赛季里所有人的 SeasonRating 从 500 起算。**历史因此天然完整保留**（D-25 的乙式归档）。

### 4. RatingTick · 积分流水

**每场对局对每位参与者产生一条。** 这是积分变动的账本。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | 标识 | |
| user_id | 引用 → User | |
| season_id | 引用 → Season | |
| match_result_id | 引用 → MatchResult | |
| delta | 数值 | 本次增减量（如 +20 / −20） |
| rating_after | 数值 | 结算后的积分值（便于追溯） |
| team_avg_before | 数值 | 结算前**本方组合平均分**（双打取平均，D-09） |
| opponent_avg_before | 数值 | 结算前对方组合平均分 |
| created_at | 时间 | |

**为什么需要这个实体**：

1. **可追溯** —— 能回答"我的积分为什么是这个数"；
2. **配置变更不影响历史** —— 若将来调整 K 值，已结算的记录保持不变（见 RatingConfig 的说明）；
3. 若不建此表，只能靠重算，任何公式调整都会**追溯性地改变历史**，与你"修改不追溯"的取向冲突（R-85）。

> **双打时**：两位搭档**各有一条** RatingTick，delta **相同**（R-97）。

### 5. RatingConfig · 等级分配置

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| id | 标识 | |
| k_factor | 数值 | **40**（R-96） |
| effective_from | 时间 | 从何时起生效 |
| note | 文本 | 变更原因 |

**为什么单独成表**：你已定"修改不追溯"的原则（R-85）。把 K 值**版本化**，将来若要调整（例如觉得波动太大），旧记录仍按当时的 K 值解释。**成本极低，收益是历史永远自洽。**

## 四、设计取舍说明

### 4.1 比赛积分为什么按赛季存，而不是存在 User 上

D-25 选了**赛季归档**（乙式）而非清零。归档的本质是"新赛季各起 500"，因此积分**天然是（用户 × 赛季）的属性**，不是用户的属性。存在 User 上会导致归档时**丢失历史**。

### 4.2 为什么需要 RatingTick（积分流水）

三个理由：可追溯、公式可演进、历史自洽。**代价**是一场比赛 N 人 → N 条流水，但这是一次批量写入，成本可控。

### 4.3 Pairing 为什么单独成实体（而不是塞进 EventRegistration）

你的回答组合出了**三种搭档形成路径**：

| 路径 | 谁发起 | 需要确认 |
| --- | --- | --- |
| 成员自行邀请搭档 | 成员 | 对方**必须**同意（R-73） |
| 单人报名，管理员后配 | 管理员 | 双方**仍需**同意（R-75） |
| 单人报名，暂未配对 | — | — |

若把搭档塞进报名记录，会出现"两条报名记录互指"的循环引用，且难以表达"配对未确认"这个中间态。**独立成实体后，三条路径共用一套状态机。**

### 4.4 为什么 MatchResult 必须挂在 Event 上

R-64 明确"**仅官方比赛**产生积分"。若允许无赛事的对局记录，就需要额外的"是否计入积分"开关 —— 而那个开关**永远是开的**。挂在 Event 上让约束成为**结构性**的，而不是靠一个布尔字段维持。

> 这也意味着：**系统里根本不存在日常对局记录** —— 日常对局功能已整体移除（[R-99](requirements.md)、[R-100](requirements.md)）。MatchResult 是唯一的对局记录，且全部属于官方比赛。

### 4.5 赛季归属为什么显式存 season_id

理论上可由对局时间落在哪个赛季区间推导。但 R-85 允许**修改赛季日期**（不追溯），若靠时间推导，改日期会让历史对局的赛季归属发生漂移 —— 与"不追溯"矛盾。**显式存储使归属稳定。**

## 五、需要你确认的三处

### ✅ 5.1 日常对局还需要记录吗？｜**已裁定：移除（选项 B，第 25 轮）**

这是**本轮最重要的确认项**。

| 事实 | 来源 |
| --- | --- |
| 日常对局**不产生积分** | R-65 |
| 排行榜的场次/胜率**只统计官方比赛** | R-70 |
| 但 D-05 的**握手确认制仍然保留** | D-05 |

**于是问题来了**：既然日常对局既不产积分、也不进任何榜单，D-05 的整套握手确认流程**还有存在意义吗？**

**已裁定：B — 移除。**

| 后果 | 说明 |
| --- | --- |
| [D-05](decisions.md) | **整体作废**，保留原文供追溯 |
| 数据模型 | **不需要**日常对局实体；MatchResult 只服务官方比赛 |
| 页面 | **不需要**"我的对局记录"页 |
| 状态机 | 少掉一套 待确认/已确认/已过期/已取消 |

**收益**：本项目的实体数、页面数、状态机数量各减一，且消除了一处逻辑空转。

### ✅ 5.2 活动名额的计数单位｜**已裁定**（第 26 轮）

**双打按队、单打按人**（R-101）。实现上用 `capacity_unit` 显式声明，**避免同一字段承载两种语义**。

### ✅ 5.3 报名截止与取消规则｜**已裁定**（第 26 轮）

| 项目 | 结论 |
| --- | --- |
| 报名取消 | **可取消** |
| 取消截止 | **比赛开始前 24 小时** |
| 签到 | **需要**，由**管理员现场确认**（[R-107](requirements.md)）；成员侧无操作 |

**签到带来的字段**：EventRegistration 增加 `checked_in_at`（见实体 11）。
