### Q31 密码重置的具体形式与限制？｜已答复 → [D-15](decisions.md)

**你的答复**：私聊发送指令"重置密码" → 机器人回复"请输入新密码" → 用户发送新密码 → 结束。**无额外校验、无频率限制、无二次确认、不影响其他登录态**。

**由此确认的定位**：QQ 号是账号安全的唯一凭据。QQ 账号安全 = 网站账号安全。

**已登记的风险**（[D-15](decisions.md)）：
- 新密码明文经过 QQ 聊天通道，会留存于聊天记录；
- 无二次确认，输错新密码即锁死 → 由 [D-16](decisions.md) 的人工通道兜底。

### ✅ Q33 机器人能否识别"是谁在私聊它"？｜已调查 → 结论见 [Q35](open-questions.md)

**结论：能识别，但拿到的很可能不是 QQ 号。**

我查证了 QQ 官方机器人文档（[单聊消息事件](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html)、[User 结构](https://bot.q.qq.com/wiki/develop/api-v2/autogen/schema/user.html)）：单聊消息事件的发送者字段提供的是 **`user_openid`**（用户 OpenID），文档中**不存在 QQ 号字段**。

| 官方平台提供的字段 | 说明 |
| --- | --- |
| `id` / `user_openid` | 用户唯一标识（**OpenID 格式**，非 QQ 号） |
| `union_openid` | 跨应用统一 OpenID（**可能为空**） |
| `username` | 用户昵称 |

**这个结果不影响架构成立，但会改变它的一处细节**：你的四处依赖（邀请码绑定、已注册去重、注册页身份带入、密码重置验证）**只需要一个稳定的用户标识**，OpenID 完全够用 —— 只要把决策里的"QQ 号"理解为"QQ 侧的稳定用户标识"。

**但它确实打破了一件事**：[D-12](decisions.md) 的登录方式之一是"**QQ 号 + 密码**"，而**用户不知道自己的 OpenID**，无法用它登录。

→ 由此产生必须回答的 **[Q35](open-questions.md)**。

### ✅ Q34 机器人侧的自定义逻辑由谁实现？｜已答复 → 你自己写（第 11 轮）

**背景**：现成的开源 QQ 机器人项目提供的是**平台能力**（收发消息、群管理、插件机制），而不会自带你需要的业务逻辑。

**你的方案需要机器人做到这些，但它们都是本项目特有的**：

| 需要的行为 | 是否现成项目会自带 |
| --- | --- |
| 收到"注册"→ 生成并绑定邀请码 → 回复邀请码与链接 | ❌ 本项目特有 |
| 重复发送返回同一条消息 / 已注册则拒绝 | ❌ 本项目特有 |
| 维护"等待用户输入新密码"的对话状态 | ❌ 本项目特有 |
| 判断发送者是否已注册（需访问网站数据） | ❌ 需要与网站对接 |
| 收发私聊消息、读取发送者身份 | ✅ 平台能力 |

**你的答复（第 11 轮）**：**自己写。**

**由此确立**：
- 机器人侧逻辑是**本项目独立于网站的一份工作量**，P2 需计入；
- 你有完全的控制权，不受现成插件能力限制；
- 上表中四项 ❌ 的逻辑全部需要自行实现。

**由此暴露的关键设计问题**（→ [Q37](open-questions.md)）：
- 机器人执行这些逻辑需要数据（邀请码、QQ 号注册状态、重置对话状态），这些数据**存在哪一侧**？
- 机器人与网站之间**谁查询谁**？

**影响面**：这是 P2 阶段**模块边界**的关键输入 —— 不解决它，模块无法划分。

### ✅ Q36 机器人账号被封的兜底方案？｜已答复 → [D-17](decisions.md)、[D-18](decisions.md)

**你的答复**：
1. **无须备用账号**
2. **不保留**注册兜底通道
3. 迁移到新账号的代价**不大**
4. （顺带答复 [Q34](open-questions.md)）机器人逻辑**自己写**

**由此确立**：机器人账号被封 → 注册与密码重置**完全停摆**，靠"换新账号"快速恢复。这是**明确接受的后果**，无第二条路径。

**合理性依据**：迁移成本低，所以用"事后快速恢复"替代"事前建兜底"。前提是迁移真的要快。

**已明确的边界**（[D-18](decisions.md)）：换号后**已注册的 QQ 号仍算已注册** —— 判定依据在网站侧，与机器人账号无关，因此换号**不需要任何数据迁移**。这也印证了"迁移代价不大"。

### ✅ Q37 机器人换号后的邀请码与数据边界？｜已答复 → [D-19](decisions.md)

**你的答复**：
1. 数据存放：**网站侧**
2. 换号前已签发未使用的邀请码：**不需要作废**

**由此确立（[D-19](decisions.md)）**：架构变为**严格单向依赖** ——

```
QQ 用户 ──私聊──▶ 机器人（薄客户端，无业务数据）
                      │ 查询 / 请求
                      ▼
                网站（唯一数据源与业务逻辑）
```

**两个收益**：
- 机器人**几乎无状态**，换号**不需要任何数据迁移** → 这正是你判断"迁移代价不大"能成立的根本原因；
- 模块边界清晰**单向**，P2 可据此划分「面向机器人的接口」这一新模块。

**⚠️ 由此产生的安全要求（重要）**：网站为机器人开放的能力中包含"按 QQ 号查询注册状态"和"重置任意用户密码"。这两项**绝不能对普通访问者开放**。

> 换句话说：[D-15](decisions.md) 之所以敢不设任何校验，前提正是**只有机器人能发起这个请求**。这是它成立的条件，必须守住。

### ✅ Q29 QQ 号是否由机器人自动带入？｜已确认：**是**（第 13 轮）

**背景**：[D-12](decisions.md) 的注册表单列出的是"姓名 / 学号 / 账户密码 / 邀请码" —— **没有 QQ 号**。而登录支持"QQ 号 + 密码"，说明 QQ 号必然被记录。

**需明确**：
- 合理推断：机器人知道发起请求的 QQ 号，因此 QQ 号**自动绑定**到邀请码上，用户无需填写。
- **若不是自动带入**，而是让用户自己填 QQ 号，则存在**账号抢注**风险：拿到邀请码的人可以填别人的 QQ 号。
- 请确认：注册页面上是否需要用户手动填 QQ 号？（建议：不需要，由邀请码携带）

**影响面**：这是账号归属的正确性问题，会直接影响邀请码的数据结构。

---


**你的答复**：注册页 QQ 号由邀请码**自动带入**，用户无需填写。

**由此确立**：注册表单只需 **姓名 / 学号 / 密码 / 邀请码** 四项。QQ 号由机器人侧确定并随邀请码携带，**用户无从伪造** → 账号抢注不可行（[D-13](decisions.md)）。

### ✅ Q52 换算规则是什么？｜已答复（第 23 轮），**但参数仍不完整**

**你的答复**（三条公式）：

| # | 规则 | 含义 |
| --- | --- | --- |
| 1 | 低胜高**多**得分 | 弱胜强，加分多 |
| 2 | 高胜低**少**得分 | 强胜弱，加分少 |
| 3 | 低输高**少**失分 | 弱负强，扣分少 |
| 4 | 高输低**多**失分 | 强负弱，扣分多 |
| 5 | **同分对局** | 双方**各自增减 20 分** |

**这四条正是标准的等级分（ELO）期望值模型** —— 得分多少与**双方实力差**挂钩，规则方向完全正确。第 5 条"同分 ±20"实际上是给这个模型定了一个**基准刻度**。

**⚠️ 但"同分 ±20"还不足以算出任意分差下的具体数值**，因为缺少把分差映射为增减量的函数。→ [Q55](open-questions.md)
