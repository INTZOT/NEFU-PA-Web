## 一、选型前的关键调查结果

### 1.1 QQ 机器人：生态正在换代（重要）

我查证了当前第三方 QQ 机器人生态，发现**协议标准正处于新旧交替期**：

| 事实 | 来源 |
| --- | --- |
| QQ 官方平台只提供 **OpenID，不给 QQ 号** | [官方文档](https://bot.q.qq.com/wiki/develop/api-v2/autogen/event/c2c_message_create.html) —— 已排除 |
| **LagrangeV2 已放弃 OneBot 11 协议**，V1 的 OneBot 11 实现**不再维护** | [Lagrange.Doc](https://lagrangedev.github.io/Lagrange.Doc/v2/) |
| Lagrange 转向自研的 **Milky 协议**（当前 1.3.0） | [Milky 文档](https://milky.ntqqrev.org/) |
| **NapCatQQ 仍在活跃发布**（v4.18.x） | [GitHub Releases](https://github.com/NapNeko/NapCatQQ/releases) |

**这对选型意味着什么**：

- ✅ **OneBot 11 依然可用**，且 NapCatQQ 是活跃的协议端实现 → **仍然可以选它**
- ⚠️ 但 OneBot 11 的**生态正在收缩**（Lagrange 已退出）
- ⚠️ Milky 是**未来方向**，但更年轻，长期维护性尚待观察

> **本项目对协议的要求极低** —— 只需要"收到私聊、知道谁发的、能回复"三件事。因此**不必追逐新协议**，选**当前最成熟、文档最全**的即可。

### 1.2 一个能显著减负的架构判断

你需要的机器人逻辑只有**三件事**：

1. 收到"注册" → 查重 → 生成邀请码 → 回复
2. 收到"重置密码" → 维护对话状态 → 写入新密码
3. 收新密码 → 落库

**这不需要插件框架。** 因此：

| 方案 | 依赖数量 | 说明 |
| --- | --- | --- |
| 引入完整机器人框架（如 NoneBot2） | 框架 + 适配器 + 插件体系 | 生态成熟，但**概念多、依赖重** |
| **协议端 + 自写的薄服务** | **仅协议端** | 三条流程自己写，约几百行，**简单且完全可控** |

> 按"便于维护"准则，**后者更优**：依赖更少、概念更少、出问题更容易定位。代价是这三条流程要自己写 —— 但本来就不复杂。

## 二、候选方案

三个方案共用：**PostgreSQL**（数据）+ **docker compose**（部署编排）+ **NapCatQQ**（QQ 协议端，Docker 运行）。

差异在**网站技术栈**与**机器人服务语言**。

### 方案甲（推荐）· Next.js 一体化 + Python 薄机器人

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 网站 | **Next.js（TypeScript）** | 生态最成熟的移动端 Web 方案；服务端 + 前端同一套代码；SEO 友好（对外名片需要） |
| 数据库 | **PostgreSQL** | 关系型、约束完备（本项目有唯一约束与唯一性兜底需求） |
| 机器人 | **Python + 一个 OneBot 客户端库** | Python 在机器人侧生态最成熟（NapCat 文档示例多为 Python） |
| QQ 协议端 | **NapCatQQ** | 活跃维护、文档全 |
| 部署 | **docker compose** | 一条命令起全部服务，重装迁移方便 |

**优点**：网站只用一种语言；机器人只为三条流程存在（**不引入插件框架**，依赖极少）。
**缺点**：机器人与网站是**两种语言**（但机器人只有几百行，且**共用同一个数据库**，无跨服务调用）。

---

### 方案乙 · 全 Python

| 层 | 选型 |
| --- | --- |
| 网站后端 | **FastAPI** |
| 网站前端 | **React**（独立构建） |
| 数据库 | PostgreSQL |
| 机器人 | **NoneBot2**（成熟框架） |
| 部署 | docker compose |

**优点**：全项目**一种语言**，心智负担单一。
**缺点**：前后端**分离构建**，部署链路比甲长；若改用服务端渲染模板，则移动端交互体验受限。

---

### 方案丙 · Node 一体化（网站 + 机器人同语言）

| 层 | 选型 |
| --- | --- |
| 网站 | Next.js |
| 机器人 | Node + OneBot 客户端库 |
| 数据库 | PostgreSQL |

**优点**：**全项目一种语言**，且是最成熟的 Web 生态。
**缺点**：Node 侧的 QQ 机器人**文档与示例不如 Python 丰富**，遇到协议问题可参考的资料更少 —— 这与"生态成熟"准则有张力。

## 四、我推荐方案甲，理由

1. **网站侧**用生态最成熟的方案 —— 直接命中你的第一优先级；
2. **机器人侧**用 Python —— 因为 QQ 机器人的**文档与社区示例以 Python 为主**，遇到问题最容易找到答案（这正是"生态成熟"的实际含义）；
3. **机器人不引入插件框架** —— 只有三条流程，引入框架是负担而非帮助（命中"便于维护"）；
4. **两者共用同一个数据库** —— 按你的决定（[R-105](requirements.md)），机器人直连数据库，因此**不需要跨服务通信**，两种语言不会带来集成复杂度；
5. **docker compose 统一编排** —— 部署、备份、迁移都简单。

**唯一的代价**：项目里有两种语言。但机器人侧只有几百行，且职责边界清晰（只碰 User、InviteCode、ResetToken 三张表）。
