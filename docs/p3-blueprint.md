## 一、仓库结构

单仓库、两个独立应用：

```
nefu-pa-web/
├── docker-compose.yml          # 统一编排：web / bot / db / napcat / caddy
├── .env.example                # 环境变量样板（不含真实凭据）
├── README.md                   # 部署与运维手册
│
├── web/                        # ① 网站（Next.js + TypeScript）
│   ├── app/
│   │   ├── (public)/           # 🟢 展示区：首页、介绍、公告、活动
│   │   ├── (member)/           # 🔵 服务区：约球、排行、个人主页、报名
│   │   ├── (admin)/            # 🟠 管理区：公告、赛事、成绩、签到
│   │   ├── (super)/            # 🔴 超管区：赛季、成员、管理员
│   │   └── api/                # 必要的接口端点
│   ├── src/
│   │   ├── modules/            # ★ 业务模块（与 P2 的 14 个模块一一对应）
│   │   ├── db/                 # 数据访问层
│   │   ├── lib/                # 通用工具
│   │   └── shared/             # ★ 与机器人共享的规则（见第三节）
│   ├── scripts/
│   │   └── seed.ts             # 初始化：创建超管账号
│   └── tests/
│
└── bot/                        # ② QQ 机器人服务（Python，薄）
    ├── bot/
    │   ├── main.py             # 入口：连接 OneBot 协议端
    │   ├── handlers.py         # 三条流程
    │   ├── db.py               # 数据库读写
    │   └── shared.py           # ★ 与网站共享的规则
    └── tests/
```

**关键点**：机器人与网站**不互相调用**，两者通过**数据库**这一共享数据源协作（[D-19](decisions.md)）。

## 三、⚠️ 一处必须提前决定的实现细节：共享规则

有两个规则**网站和机器人都要用**，且**必须完全一致**：

| 规则 | 网站用它做什么 | 机器人用它做什么 |
| --- | --- | --- |
| **密码加密** | 校验登录密码 | **写入**新密码（重置流程） |
| **邀请码生成** | 注册时校验 | **生成**邀请码 |

**如果两边实现不一致，会出现致命故障**：机器人生成的邀请码网站认不出；机器人写入的密码用户登录不了。

**两种做法**：

| 做法 | 说明 | 评价 |
| --- | --- | --- |
| **甲：单一实现 + 机器人调用** | 密码与邀请码规则只在网站实现；机器人通过一个**极小的**本地接口请求它 | ✅ **推荐** —— 规则只有一处，不可能不一致 |
| 乙：两边各写一份 | 网站用 TS、机器人用 Python 各实现一次 | ⚠️ 两份代码必须永远同步，**是长期隐患** |

> **我推荐甲**：虽然这会给机器人增加一个调用网站的动作，但它把**最容易出错的一致性风险**彻底消除。这与便于维护准则一致 —— 宁可多一个接口，也不要两份必须手工同步的加密逻辑。

**⏳ 这一处需要你点头**，因为它轻微偏离了"机器人只直连数据库"的原始设想。

## 四、实施顺序

分 7 个阶段，每个阶段结束都有**可验证的产出**：

| 阶段 | 内容 | 验证方式 |
| --- | --- | --- |
| **1. 地基** | 仓库结构、docker compose、PostgreSQL 起库、数据库表结构 | 一条命令起服务，表建成 |
| **2. 账号体系** | 注册页、登录、会话、超管初始化 | 能注册、能登录、超管身份正确 |
| **3. 机器人** | NapCatQQ 接入、三条流程、共享规则 | 在 QQ 里发注册能拿到邀请码并完成注册 |
| **4. 展示区** | 首页、介绍、公告（含管理端发布） | 游客能看到公告 |
| **5. 活动** | 赛事发布、报名、候补、搭档配对、签到 | 完整走一遍报名到签到 |
| **6. 约球** | 房间、申请、审批、状态机 | 完整走一遍发起到满员到过期 |
| **7. 积分** | 对局录入、ELO 结算、排行榜、赛季归档 | 录一场比赛，积分正确变化；跨赛季验证 |

**顺序理由**：

- 账号体系最先，因为**它是所有服务区功能的前提**；
- 机器人紧随其后，因为**它是唯一的注册入口** —— 没有它连测试账号都建不了；
- 约球与积分放后面，因为它们**互不依赖**（[P2 依赖图](p2-modules.md) 中 C 与 E 无连线），可以最后做。
