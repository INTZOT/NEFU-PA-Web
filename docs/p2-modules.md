## 一、模块划分

### 1.1 十四条模块

| 代号 | 模块 | 职责 | 准入 |
| --- | --- | --- | --- |
| **A** | 展示区 | 社团介绍、公告浏览、活动浏览 | 🟢 公开 |
| **B** | 账号与身份 | 注册、登录、密码、换绑、角色 | 🟢 / 🔵 |
| **C** | 约球 | 房间、申请、审批、退出、取消、过期 | 🔵 成员 |
| **D** | 活动与报名 | 赛事发布、报名、候补、搭档配对 | 🔵 / 🟠 |
| **E** | 积分结算 | 对局录入、ELO 结算、流水 | 🟠 管理 |
| **F** | 排行榜 | 积分榜、场次/胜率榜、赛季切换 | 🔵 成员 |
| **G** | 赛季 | 起止配置、自动归档、历史查询 | 🔴 超管（配置） |
| **H** | 公告管理 | 发布、编辑、置顶 | 🟠 管理 |
| **I** | 成员与权限管理 | 成员列表、人工兜底、管理员设置 | 🔴 超管 |
| **J** | 机器人对接 | 邀请码签发、注册状态查询、密码重置 —— **通过直连数据库实现**（第 27 轮） | 内部 |
| **K** | 个人主页 | 自评分维护、赛季成绩、账号凭据 | 🔵 成员 |

**其中 J 是唯一对外（对机器人）开放的模块，也是账号体系的安全边界。**

> ⚠️ **第 27 轮修订**：J 不再是一组"网站暴露的 API"，而是**机器人直连数据库读写**。因此 J 的边界不是接口，而是**共享的数据层 + 双方共同遵守的表结构契约**。见 [D-19](decisions.md)。

### 1.2 依赖方向

**严格单向，无循环依赖。**

```
        A 展示区          B 账号与身份          H 公告管理
          │                    │                    │
          └────────┬───────────┴──────────┬─────────┘
                   ▼                      ▼
              D 活动与报名            C 约球
                   │
                   ▼
              E 积分结算 ──▶ G 赛季
                   │
                   ▼
              F 排行榜

   J 机器人对接 ──▶ B 账号与身份
   K 个人主页  ──▶ F 排行榜（读取赛季成绩）
   I 成员与权限 ──▶ B 账号与身份
```

**关键特征**：

| 特征 | 说明 |
| --- | --- |
| **E 是唯一写入积分的模块** | 其他模块只能读取积分（F、K） |
| **J 只依赖 B** | 机器人对接不碰业务，只碰身份（D-19） |
| **C 与 D 互不依赖** | 两条业务线独立（D-03），这点在模块层面得到保持 |
| **G 被 E 依赖** | 结算需要知道当前赛季 |

> **C 与 E 之间没有任何连线** —— 约球与积分完全无关。日常对局功能已整体移除（[R-99](requirements.md)），因此不存在"约球产生积分"的路径。

| **无"对局确认"环节** | [D-05](decisions.md) 作废后，对局只由 E 单向写入（管理员录入），**无确认回路** |

## 二、关键流程

### 2.1 注册与绑定（D-12、D-13）

```
用户在 QQ 私聊机器人
      │ 发送"注册"
      ▼
机器人 ──▶ J：查询该 QQ 号是否已注册
      │
      ├─ 已注册 ──▶ 回复"你已注册过"（拒绝）
      ├─ 已有邀请码 ──▶ 返回同一条消息（同一个码）
      └─ 首次 ──▶ J 生成 InviteCode（绑定该 QQ 号）──▶ 返回邀请码 + 注册链接
      ▼
用户打开注册页，填：姓名 / 学号 / 密码 / 邀请码
      │
      ▼
B：校验邀请码 → 取其中的 QQ 号（**用户无需填 QQ 号**，D-12）
      │
      ▼
创建 User + SeasonRating（当前赛季，rating = 500）
      │
      ▼
引导：滑动选择自评分（0–1000，五档话术，D-21）
```

**要点**：QQ 号**由邀请码带入**，用户无从伪造 → 无抢注风险（R-35）。

---

### 2.2 密码重置（D-14、D-15）

```
用户私聊"重置密码"
      ▼
机器人 ──▶ J：按 QQ 号查用户
      ├─ 未注册 ──▶ 拒绝
      └─ 已注册 ──▶ 创建 ResetToken（awaiting_new_password）──▶ 回复"请输入新密码"
      ▼
用户发送新密码
      ▼
机器人 ──▶ J：提交新密码 ──▶ B 更新密码，ResetToken 置为 done
      ▼
回复"已重置"
```

**无校验、无频率限制、无二次确认**（D-15，明确接受）。
**安全前提**：J 模块**不得对普通访问者开放**（D-19、R-51）—— 否则任何人都能重置他人密码。

---

### 2.3 比赛结算（D-09、D-20）

```
线下：比赛结束，拿到成绩
      ▼
管理员在"成绩录入"页逐场录入：赛事 / 赛制 / A 方人员 / B 方人员 / 胜方
      ▼
E 模块（每场）：
  1. 取当前赛季 → 取各方 SeasonRating
  2. 计算组合平均分（双打取两人平均，D-09）
  3. 按 ELO 公式算 Δ：
       E = 1 / (1 + 10^((对手组合分 − 本方组合分) / 400))
       Δ = 40 × (实际结果 − E)
  4. 更新双方 SeasonRating.rating；胜方 wins+1、负方 losses+1
  5. 为**每位参与者各写一条 RatingTick**（双打两人 delta 相同）
      ▼
F 排行榜数据随之更新（只读）
```

**不可撤销**：录入即结算，无撤销路径（D-05 的精神、Q20 待定）。

---

### 2.4 赛季归档（D-25）

```
系统按配置时间检查（学年结束当天）
      ▼
G：把当前 Season.status 置为 archived
      ▼
创建新 Season（name 如 "2027/2028"，状态 active）
      ▼
**不修改任何历史数据** —— 新赛季中各人的 SeasonRating 从 500 起算
      ▼
排行榜默认显示新赛季；历史赛季仍可切换查看
```

**归档是"开新的"，不是"清旧的"** —— 这是乙式归档（D-25）的核心。

---

### 2.5 约球房间生命周期（D-10）

```
成员发起房间（时间段 / 人数上限 / 备注）
      ▼
状态 = open ──▶ 其他人申请（RoomApplication = pending）
      ▼
发起人审批 ──┬─ 同意 ──▶ approved ──▶ 已批准人数 = capacity ？
             └─ 拒绝 ──▶ rejected        ├─ 是 ──▶ 状态 = full（锁死，不再接受申请）
                                          └─ 否 ──▶ 保持 open
      ▼
已加入者退出 ──▶ 空位恢复 ──▶ 状态回到 open
      ▼
24 小时到 ──▶ expired（或发起人取消 ──▶ cancelled）
```

**这是全项目状态最复杂的流程**（三处双向转换：满员↔空位、open↔full）。

---

### 2.6 双打搭档配对（D-20、R-73~R-75）

```
路径一：成员自行邀请
  成员 A 在报名时指定搭档 B
      ▼
  创建 Pairing（initiated_by = A，proposed_by = member，status = pending）
      ▼
  B 收到待确认 ──┬─ 同意 ──▶ confirmed ──▶ 占 1 队名额
                 └─ 拒绝 ──▶ rejected

路径二：单人报名 + 管理员后配
  成员 A 单人报名（无搭档）
      ▼
  管理员选择 B ──▶ 创建 Pairing（proposed_by = admin，status = pending）
      ▼
  **A 与 B 双方均需同意** ──▶ confirmed ──▶ 占 1 队名额
```

> **第 25 轮更新**：机制 3 已随 [D-05](decisions.md) 作废而**消失**，现在只剩**两套**。收敛价值下降，但统一状态语义仍有意义。

### 建议：**统一状态语义，但不强求合并表**

| 层面 | 建议 | 理由 |
| --- | --- | --- |
| **状态枚举** | 统一为：`pending` / `accepted` / `rejected` / `cancelled` / `expired` | 三处语义一致，减少心智负担 |
| **过期规则** | 统一采用 24 小时（与约球房间一致） | 项目内已有 24h 的节奏约定 |
| **数据表** | **不合并** | 三者的业务字段差异大（房间/赛事/用户），合并会造成大量空字段 |
| **操作** | 统一的"同意 / 拒绝"动作语义 | 界面与交互可复用同一套组件形态 |

> **如果 5.1 的结论是"移除日常对局"，那机制 3 直接消失，只剩两套** —— 收敛价值会小很多，但统一状态枚举仍然值得。

## 四、机器人对接（J 模块 · 直连数据库）

**第 27 轮定案**：机器人**直接读写数据库**，网站不暴露专属 API。

### 4.1 机器人需要完成的操作

| 操作 | 读 / 写 | 涉及实体 | 业务规则（**机器人侧需自行实现**） |
| --- | --- | --- | --- |
| 查询某 QQ 号是否已注册 | 读 | User | 按 qq_number 查询 |
| 查询是否已有邀请码 | 读 | InviteCode | 按 qq_number 查询 |
| 生成并绑定邀请码 | 写 | InviteCode | **一码一 QQ**；已注册则拒绝 |
| 创建用户 | 写 | User、SeasonRating | 校验邀请码；QQ 号**由邀请码带入**；新赛季积分置 500 |
| 更新密码 | 写 | User | **加密方式必须与网站一致** |
| 维护重置会话 | 写 | ResetToken | 等待输入新密码的状态 |

### 4.2 必须满足的约束

| 约束 | 说明 |
| --- | --- |
| **专用受限数据库账号** | 绝不能用管理员账号；只授予必需的表与操作 |
| **密码加密规则统一** | 机器人写入的密码必须与网站可验证的格式一致 |
| **表结构是共享契约** | 网站改表必须同步改机器人，否则机器人查询会失效 |
| **唯一性靠约束保证** | "一个 QQ 号只能注册一次"应由数据库约束兜底，而非依赖机器人判断正确 |

### 4.3 安全约束

| 要求 | 说明 |
| --- | --- |
| 数据库凭据不外泄 | 该凭据**等同于可重置任意用户密码**的能力 |
| 不暴露给前端 | 凭据绝不出现在任何网页、客户端或公开渠道 |
| 最小权限 | 机器人账号只应有完成上表操作所需的权限 |

> ⚠️ **这是全系统最敏感的一处** —— 持有该数据库凭据即可重置任意账号密码。[D-15](decisions.md) 之所以敢"不设任何校验"，正是因为这里收了口：**安全性来自"只有机器人能连上"**。
