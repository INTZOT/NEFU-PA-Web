## 一、你给的优先级（第 29 轮）

> **生态成熟、组件成熟、便于维护优先，其次性能。**

翻译成可判断的准则：

| 排序 | 准则 | 具体含义 |
| --- | --- | --- |
| **1** | **生态成熟** | 遇到问题时能搜到答案；有活跃社区；不会用着用着没人维护了 |
| **1** | **组件成熟** | 需要的功能**有现成的轮子**，不必自己造 |
| **2** | **便于维护** | 你一个人能hold住；依赖少；升级不折腾 |
| **3** | 性能 | **不是首要目标** |

### ⚠️ 这条优先级有一个重要推论

**"性能不是首要目标"是合理的，因为本项目的数据量与并发都极小**：

| 指标 | 量级 |
| --- | --- |
| 成员数 | 一个社团，**几十到几百人** |
| 赛事数 | 每学年**几场到十几场** |
| 对局数 | 每场赛事**十几到几十场** |
| 同时在线 | 几乎不可能超过**个位数** |

> 在这个量级上，**任何主流技术都能轻松胜任**。因此"性能"确实应该排在最后 —— 它是**约束**（够用即可），不是**优化目标**。
>
> 真正决定项目成败的是：**你能不能长期维护它**。

## 三、评估维度（用于后续对比方案）

选定具体方案时，按这些维度评分：

| 维度 | 权重 | 判断方式 |
| --- | --- | --- |
| **生态活跃度** | 🔴 高 | 最近提交时间、issue 响应速度、社区规模 |
| **组件齐全度** | 🔴 高 | 需要的功能是否开箱即用 |
| **单人可维护性** | 🔴 高 | 概念数量、学习曲线、文档质量 |
| **与硬约束的匹配** | 🔴 高 | 见第二节，一条不满足即淘汰 |
| **你的熟悉程度** | 🟡 中 | 见待补输入 |
| **部署复杂度** | 🟡 中 | 见待补输入 |
| **成本** | 🟡 中 | 见待补输入 |
| 性能 | 🟢 低 | 够用即可 |

## 四、待补输入（缺失则无法定案）

### 🔴 输入 A：部署条件（[Q5](open-questions.md)，你一直未答）

| 问题 | 为什么关键 |
| --- | --- |
| 有没有**学校提供的服务器**？ | 若有，可能限定在某些技术环境内 |
| 是否需要**校外可访问**？（涉及备案） | 影响部署形态，甚至影响可行性 |
| 有没有**域名**？ | 没有域名只能走 IP 或免费子域，影响体验 |
| **经费预算**多少？ | 决定能否用托管服务，还是必须自建 |
| 你愿意**自己管服务器**吗？ | 若不愿意，方案要偏向托管式 |

### 🔴 输入 B：你的技术背景

| 问题 | 为什么关键 |
| --- | --- |
| 你**熟悉哪些语言 / 技术**？ | **这比任何技术优劣都重要** —— 你一个人维护，选你不会的等于自找麻烦 |
| 有没有**排斥**的技术方向？ | 避免选完你不愿意碰 |
| 你打算**投入多少时间**学习？ | 决定能否引入需要学习的新技术 |

> 💡 **说明**：项目已明确"便于维护优先"。而在单人维护的场景下，**"你熟悉"是"便于维护"的最大权重项** —— 一个生态再好但你不会的技术，维护成本远高于一个普通但你熟练的技术。
