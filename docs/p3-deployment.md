## 一、服务拓扑

一台服务器上跑五个容器，用 docker compose 统一编排：

```
                    互联网
                       │
                       ▼
              ┌─────────────────┐
              │  caddy (HTTPS)  │  ← 自动证书，80/443
              └────────┬────────┘
                       │
                       ▼
              ┌─────────────────┐
              │ web (Next.js)   │  ← 网站，仅内网暴露
              └────────┬────────┘
                       │
        ┌──────────────┼──────────────┐
        ▼              ▼              ▼
  ┌──────────┐  ┌────────────┐  ┌──────────┐
  │    db    │  │    bot     │  │ napcat   │
  │Postgres  │◀─│  Python    │◀─│ OneBot   │
  └──────────┘  └────────────┘  └──────────┘
        ▲                             ▲
        └─────────────────────────────┘
           bot 与 web 共用同一个数据库
```

| 服务 | 对外暴露 | 说明 |
| --- | --- | --- |
| **caddy** | ✅ 80 / 443 | 反向代理 + 自动 HTTPS 证书 |
| **web** | ❌ 仅内网 | 网站本体 |
| **db** | ❌ 仅内网 | PostgreSQL，数据卷持久化 |
| **bot** | ❌ 仅内网 | 机器人逻辑 |
| **napcat** | ⚠️ 仅本机 | QQ 协议端，需扫码登录 |

**安全要点**：除 caddy 外**任何服务都不对公网开放端口**。数据库尤其不能暴露。

## 二、⚠️ NapCatQQ 的实际运维负担（必须提前知道）

这一项是本项目**唯一需要你周期性手动干预**的地方，我在 [D-17](decisions.md) 里已按你的选择记录为"接受"，但具体是什么样，你需要清楚：

| 事项 | 说明 |
| --- | --- |
| **首次登录需扫码** | 你需要用手机 QQ 扫码登录协议端 |
| **会话会失效** | QQ 登录态可能过期、被踢下线，**需要重新扫码** |
| **账号有被封风险** | 第三方协议端属灰色地带（[D-17](decisions.md) 已接受此风险） |
| **被封后无备用方案** | 你选择不设兜底（[D-17](decisions.md)）—— 换新账号即可恢复 |
| **换号不需迁移数据** | 数据全在数据库，新账号接上同一套逻辑即可（[D-18](decisions.md)） |

**实践建议**：

| 建议 | 理由 |
| --- | --- |
| 用一个**专门的 QQ 号**做机器人，不要用你个人的主号 | 降低个人损失 |
| 把它拉进社团群后**保持群内存在** | 它是准入的唯一入口 |
| 定期检查协议端是否在线 | 掉线期间新人无法注册 |

> ⚠️ **这是本项目最脆弱的一环** —— 不是技术问题，而是外部依赖问题。技术上已尽量隔离（数据不依赖它），但**注册与密码重置会随它一起停摆**。

## 三、域名与 HTTPS

| 项目 | 说明 |
| --- | --- |
| 域名解析 | 把你的域名 A 记录指向服务器 IP |
| 备案 | 你自理（国内服务器必须） |
| HTTPS | **caddy 自动申请并续期**证书，无需手工配置 |
| 强制跳转 | HTTP 自动跳 HTTPS |

> **为什么用 caddy**：证书自动管理是本项目里省事最多的一项 —— 证书过期导致的网站不可用是自建站的常见故障，caddy 从根本上消除了它。

## 四、备份与恢复

项目的数据**全部在 PostgreSQL 里**（含账号、积分、赛季、赛事），因此备份策略很简单：

| 项目 | 方案 |
| --- | --- |
| 备份对象 | 仅 PostgreSQL 数据卷 |
| 备份方式 | 定时 dump 到宿主机目录（可再加云存储） |
| 备份频率 | 建议每日一次（数据量极小，成本可忽略） |
| 保留策略 | 保留最近若干份，滚动覆盖 |
| 恢复 | 从 dump 还原即可，**无需恢复其他任何东西** |

**为什么不备份其他**：网站与机器人的代码在仓库里，配置在 @.env@ 里，两者都可重建。**唯一不可重建的是数据。**

## 五、环境变量与凭据

所有凭据集中在 @.env@（不进仓库，提供 @.env.example@ 样板）：

| 变量类别 | 用途 |
| --- | --- |
| 数据库连接 | web 与 bot **各用一个账号**（bot 用受限账号，见 [D-19](decisions.md)） |
| 会话密钥 | 登录态签名 |
| 域名 | caddy 配置 |
| NapCat 连接信息 | bot 连接协议端 |
| 超管初始信息 | 首次初始化用（[D-23](decisions.md)：超管**预先指定**） |

> ⚠️ **超管账号必须预先指定**（[D-23](decisions.md)），不能靠"第一个注册的账号"。因此初始化时会由脚本创建，而不是等有人注册。
