## D-01 身份与准入：QQ 群是唯一入口，网站不做成员名单校验

**决策**：网站的非展示部分**仅对社团成员开放**。但**网站自身不维护、不校验群成员名单** —— 准入在第一道门（QQ 群 + 机器人注册）完成判定，此后不再复核。

**备选与取舍**：
- 网站同步群成员名单并持续校验 → 需要外部名单来源，是本项目最大的不确定依赖。
- **入口一次判定、网站不复核**（采纳）→ 无外部依赖，架构大幅简化。

**对架构的影响**：
- ~~"成员名单同步"这一耦合点被消除~~（原 Q12 为最高优先级阻塞项，现已解除）。
- 权限模型收敛为**游客 / 成员**两层（管理员是成员的精化），不存在"待审核用户"这一类中间态。
- 账号一旦创建即长期有效。

**明确接受的结果（不处理）**：成员退群、毕业离群后，其账号与历史数据**保持原样**，不冻结、不清除、不追溯。

**由此产生的新约束**：**QQ 机器人是整个系统的准入门（单点）**。机器人若失效，新成员将无法注册。这是运营层面的关键依赖，需要在实施阶段重点对待。

## D-02 展示与服务的边界

**决策**：网站划分为两个区域，准入不同。

| 区域 | 内容 | 准入 |
| --- | --- | --- |
| 展示区 | 社团介绍、社团公告、活动信息（公开部分）等 | 游客可访问 |
| 服务区 | 个人资料、报名操作、约球、积分对局录入等 | 仅成员 |

**备选与取舍**：
- 全站需登录 → 牺牲"对外名片"的定位，新生与校方无法直接查看。
- **分区准入**（采纳）→ 保住对外名片功能，同时把敏感操作收进成员区。

**对架构的影响**：
- 每个页面从设计之初就要标注准入级别，这是信息架构（P2）的必要输入。
- 公告、活动、排行榜等模块需要明确"哪些字段对游客可见"（见 Q17）。

## D-03 官方活动与约球为两条独立业务线

**决策**：**不合并**。两者独立建模、独立页面、独立规则。

| | 官方活动 | 约球 |
| --- | --- | --- |
| 发起人 | **仅管理员** | **任何成员** |
| 形态 | 官方发布，参考"开球网"式活动页 | 游戏大厅：发起房间 → 他人申请 → 发起人同意 |
| 时间 | 官方指定时间与场地 | 发起人填写**时间段** |
| 名额 | 待定（见 Q16） | **人数上限**，满员锁死 |
| 与积分关系 | 无校验 | **不校验**，积分仅供参考 |

**备选与取舍**：
- 统一为"一个可报名的球局" → 模型更小，但官方活动与大厅约球的交互形态差异较大，统一会牺牲各自的表达力。
- **保持两条业务线**（采纳）→ 模型与页面更多，但每条规则都更简单、更贴合场景。

**对架构的影响**：
- 这是目前**最影响工作量**的决策：两条业务线意味着两套模型、两套页面、两套状态机。
- 约球的房间生命周期（见 [D-10](#d-10-约球房间的字段与生命周期)）是整个项目中状态最复杂的部分。

### 休赛期的作用范围（第 19 轮明确）

[D-25](#d-25-赛季为一级实体按学期自动归档) 确定的"寒暑假为休赛期"**只约束官方活动**：

| | 官方活动 | 约球 |
| --- | --- | --- |
| 休赛期是否可开展 | **否** | **不受限制** |
| 理由 | 官方赛事需要组织与场地 | 成员自助，不依赖社团组织 |

> 这是两条业务线独立的又一个体现 —— 休赛期是**官方赛事的休眠**，而不是**整个服务区的休眠**。约球在假期照常可用。

## D-04 积分定位为参考性荣誉系统

**决策**：积分**仅用于参考与展示**，不参与任何准入校验、不参与约球匹配、不影响报名资格。

**备选与取舍**：
- 积分作为约球水平匹配依据 → 需要匹配算法与活跃度门槛。
- 积分作为报名优先权 → 引入公平性争议。
- **纯参考展示**（采纳）→ 大幅降低复杂度。

**对架构的影响**：
- 积分模块在架构上是**只读消费者**：读取对局结果，不被其他模块依赖。可独立演进甚至延后上线。
- 积分刷分、自报初始分不准等问题，破坏面被**隔离在积分模块内部**，不会污染其他功能。

## 原 D-05 对局采用双方握手确认制，无审核

**决策**：对局结果由**双方共同互认**，完成握手后即确定最终战果，**无须管理员审核**。

**完整状态流转（Q13）**：

| 环节 | 规则 |
| --- | --- |
| 发起 | **任一方**均可发起录入 |
| 修正 | 对方确认前，**双方均可撤回或修改** |
| 时限 | **24 小时内**需完成确认，超时自动失效 |
| 争议 | 任一方可**单方面取消**本次录入，作为唯一出口 |
| 生效 | 双方确认后**立即生效并结算积分** |
| 身份核验方式 | 凭**真实 QQ 号**确认身份（由 [D-17](#d-17-机器人采用第三方框架身份锚点为真实-qq-号) 确定） |
| 撤销 | **不支持**。已确认的对局不可撤销，积分不可回退 |

**备选与取舍**：
- 胜方提交 + 管理员审核 → 单人维护下会成为长期负担。
- 单方提交即生效 → 易产生争议与虚报。
- **双方握手 + 争议可单方取消 + 生效后不可撤销**（采纳）→ 免除审核人力，状态机极简，且天然防止"一方被强行记账"。

**对架构的影响**：
- 对局状态可归纳为：**待确认 → 已确认**，以及两个终结分支：**已过期**、**已取消**。
- "争议"不需要特殊状态 —— 取消本身就是争议的出口，这是本设计中很省事的一点。
- 确认后的记录是**不可变的**，只可追加不可修改。

### ⚠️ 与积分的解耦（第 15 轮）

因 [D-09](#d-09-积分体系规则自报初始分不重置单双合并) 明确**比赛积分仅由官方比赛产生**，本条握手确认制的**职责范围发生了变化**：

| | 说明 |
| --- | --- |
| 握手确认仍然保留 | 日常对局依然需要双方互认才生效 |
| **但不再产生积分** | 握手确认的结果**不进入任何积分** |
| 它的作用 | 留下**对局记录**；若排行榜含"场次/胜率"且计入日常对局，则为其提供数据（见 [Q44](open-questions.md)） |

**这带来一个正面效果**：原"双方合谋刷分"的风险**大幅降低** —— 因为日常对局根本不影响积分。积分只由官方比赛产生，而官方比赛由管理员组织、有赛制约束。

### 结算公式（第 24 轮定案：标准 ELO）

**你把规则定为"标准 ELO"，因此以下参数全部按标准定义确定，无需再逐项设计。**

**公式**：

```
期望胜率  E = 1 / (1 + 10^((R对手 − R自己) / 400))
积分变化  Δ = K × (实际结果 − E)        K = 40
          实际结果：胜 = 1，负 = 0
```

**你给的五条规则，全部由该公式自然满足**：

| 你的规则 | 公式中的体现 |
| --- | --- |
| 低胜高多得 | 弱者 E 小 → (1 − E) 大 → Δ 大 |
| 高胜低少得 | 强者 E 大 → (1 − E) 小 → Δ 小 |
| 低负高少失 | 弱者 E 小 → −E 小 → 扣得少 |
| 高负低多失 | 强者 E 大 → −E 大 → 扣得多 |
| 同分各 ±20 | 同分时 E = 0.5 → Δ = 40 × (±0.5) = **±20** ✅ |

**具体数值示例**（便于校对实现）：

| 分差（强者 − 弱者） | 弱者胜 | 强者胜 |
| --- | --- | --- |
| 0 | +20 / −20 | +20 / −20 |
| 100 | +26 / −26 | +14 / −14 |
| 200 | +30 / −30 | +10 / −10 |

> **勘误（第 61 轮）**：原表为「100 → +32 / +8」「200 → +38 / +2」，**与本条给出的公式不符**。
> 按公式重算：分差 100 时 `10^(100/400) = 1.778` → 弱者胜 `Δ = 40×(1 − 1/2.778) ≈ +26.0`、强者胜 `≈ +14.0`；
> 分差 200 时 `10^(200/400) = 3.162` → 弱者胜 `≈ +30.4`、强者胜 `≈ +9.6`。
>
> **判定以公式为准**，理由：
> 1. 公式是本条的**正式规则**，且明确写入「标准 ELO」的定性 —— `400` 即标准 ELO 的分母；
> 2. 公式能推出另一条**独立依据**（你亲自定的「同分 ±20」）：`K=40 × (1 − 0.5) = ±20` ✅；
> 3. 原示例表只是「便于校对实现」的辅助材料，无独立依据 —— 是它算错了，而非公式错了；
> 4. 实测本条声称的「五条规则全部由公式自然满足」这句话本身成立（低胜高多得、高胜低少得、低负高少失、高负低多失、同分 ±20 全部吻合）。
>
> 实现按公式（分母 400）完成，并已用本表逐值校对。

**同时确定的其他参数**：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| K 值 | **40** | 由"同分 ±20"直接确定 |
| 是否零和 | **是** | 一方 +X，另一方必 −X（标准 ELO 性质） |
| 双打组合分 | 搭档双方积分**取平均** | [D-09](#d-09-积分体系规则自报初始分单双合并重置条款已修订) 原条款 |
| 双打两人增减 | **相同**（第 24 轮确认） | 算出一个 Δ，两人各 +Δ 或各 −Δ |

**已知的极端情况（接受）**：分差极大时，强胜弱的 Δ 趋近 0（如分差 400 → 仅 +0.5）；反过来弱胜强可接近 +40。这是标准 ELO 的正常行为。

**待明确**：无。结算规则已完整、可实现。

| 方式一 | **QQ 号 + 密码** |
| 方式二 | **学号 + 密码** |

> ✅ **已确认（[D-17](#d-17-机器人采用第三方框架身份锚点为真实-qq-号)）**：因采用第三方框架，机器人可获得**真实 QQ 号**，故"QQ 号 + 密码"这一登录方式**成立并保留**。两种登录方式均有效。

**备选与取舍**：
- 直接开放网页注册 → 与 [D-01](#d-01-身份与准入qq-群是唯一入口网站不做成员名单校验) 的"群准入"定位冲突，任何人都能注册。
- 机器人内直接完成注册（一问一答式收集） → 交互冗长，且收集密码等信息在聊天窗口内不合适。
- **邀请码 + 网页填表**（采纳）→ 用一次性的邀请码把"群成员"这一准入条件带到网页端，同时保留了良好的表单填写体验。

**对架构的影响**：
- **邀请码是本系统的实质性安全边界。** 它是"人在群里"这一事实的唯一凭证载体。
- 机器人职责从"回答注册请求"扩展为"**签发准入凭证**"，比 [D-07](#d-07-qq-机器人职责范围限于注册与绑定) 描述的更具体。
- 注册是一个**跨端的两段式流程**：QQ 端获取凭证 → 网页端消费凭证。凭证的时效与消费规则必须明确（Q27）。
- QQ 号是**注册时自动带入**的（因为机器人知道是谁在向它发起请求），理论上**不需要用户在表单里填写** → 这一点必须确认，否则会留下账号被抢注的口子（Q29）。

**邀请码规则（Q27 已答复，详见 [D-13](#d-13-邀请码与-qq-号一次性永久绑定不设有效期)）**：邀请码在用户首次发送"注册"时即与该 QQ 号**永久绑定**，**不设有效期**；重复发送"注册"返回同一条消息；该 QQ 号已注册则**拒绝**。

**由此产生的空白**：
1. **密码找回**：已由 [D-14](#d-14-机器人职责扩展为账号身份锚点) 确定为"通过机器人重置"。
2. 初始积分确认步骤的位置：你在 [D-09](#d-09-积分体系规则自报初始分不重置单双合并) 中说"注册后自行确认"，尚未明确是注册流程的一步，还是注册后单独的引导（Q30）。

## D-13 邀请码与 QQ 号一次性永久绑定，不设有效期

**决策**：

| 项目 | 规则 |
| --- | --- |
| 绑定时机 | 用户**首次发送"注册"**时，即为该 QQ 号生成并绑定邀请码 |
| 身份标识的实际形态 | **真实 QQ 号**（由 [D-17](#d-17-机器人采用第三方框架身份锚点为真实-qq-号) 确定）。QQ 号对用户可见，因此既是绑定凭据也是登录标识 |
| 有效期 | **不设有效期**（永久有效） |
| 重复申领 | 重复发送"注册" → 返回**同一条消息**（同一个邀请码） |
| 已注册的 QQ | 再次发送"注册" → **拒绝** |
| 作用域 | 邀请码**仅绑定到一个 QQ 号**，不可转让给他人使用 |

**备选与取舍**：
- 一次性邀请码 + 短有效期 → 更严格，但会引入"过期后重新申领"的往返，用户被打断时需重来。
- **永久绑定到单一 QQ 号**（采纳）→ 用户随时可回来完成注册，体验更宽容；安全边界由"一码一 QQ"承担，而非由时效承担。

**对架构的影响**：
- 邀请码是一个**长期存在的持久化对象**，不是临时令牌 → 需要被存储，而非仅存在于会话中。
- 邀请码与 QQ 号是**一对一**关系，本身即构成"一人一码"。
- "重复发送返回同一条消息"意味着需要**记忆并复现**该消息内容 → 邀请码必须是已持久化的数据。**精化（第 12 轮）**：该数据存放于**网站侧**（[D-19](#d-19-邀请码与注册状态数据由网站侧持有机器人是薄客户端)），机器人每次向网站查询 —— 因此"记忆"的责任在网站，不在机器人。

### ⚠️ 明确接受的风险：邀请码泄露即等于准入失守

由于邀请码**永久有效且可反复查看**，任何获得它的人都可以：

1. 用该邀请码**注册一个账号**，并借由 [D-12](#d-12-注册采用机器人发放邀请码--网页填表的两段式流程) 的自动带入机制 **冒充该 QQ 号**；
2. 从而**抢先占用**这个 QQ 号对应的账号位。

**因此邀请码是本系统最需要保护的信息**：

| 保护要求 | 说明 |
| --- | --- |
| 仅私聊可见 | 注册必须为**私聊**交互，邀请码**绝不能在群聊中回复或展示** |
| 不对外展示 | 邀请码不得出现于网页、个人主页、分享内容或任何公开位置 |
| 按凭据对待 | 邀请码等同于**密码级别**的敏感信息 |

**待明确**：~~重置密码的具体形式与频率限制（Q31）；QQ 死局的兜底（Q32）~~ → 均已答复，见 [D-15](#d-15-密码重置为纯对话式流程无额外校验) 与 [D-16](#d-16-保留管理员人工兜底通道)。

## D-14 机器人职责扩展为"账号身份锚点"

**决策**：**正式复议并取代** [D-07](#d-07-qq-机器人职责范围限于注册与绑定) 中"机器人仅限注册与绑定"的边界。机器人现在的完整职责为：

| 职责 | 说明 | 引入阶段 |
| --- | --- | --- |
| 签发邀请码 | 首次发送"注册"时生成并与 QQ 号绑定 | [D-12](#d-12-注册采用机器人发放邀请码--网页填表的两段式流程) |
| 提供注册入口 | 返回注册页面链接 | [D-12](#d-12-注册采用机器人发放邀请码--网页填表的两段式流程) |
| **重置密码** | 忘记密码时，用户通过机器人重置（**Q28 选 A**） | 本条 |
| ~~通知推送~~ | **仍不做** | — |
| ~~业务操作~~ | **仍不做**（报名、约球、查积分一律在网站） | — |
| ~~公告/活动同步到 QQ 群~~ | **仍不做**（第 13 轮明确：双端**手动同步**） | 第 13 轮 |

**备选与取舍**：
- 无找回 / 人工找回 → 与单人维护冲突，且"忘记密码"必然发生。
- **由机器人承担身份验证通道**（采纳）→ 复用已有的 QQ 绑定关系，零额外成本，且机器人本来就是准入的起点。

**对架构的影响**：
- **机器人成为长期基础设施，而非一次性门禁。** 它的可用性同时影响：新成员能否注册、老成员能否找回密码。
- 网站与 QQ 侧的关系从"一次性交割"变为"**注册时交割成员判定权，长期保留身份验证能力**"（见 [D-08](#d-08-注册在-qq-内完成所有权一次性交割给网站) 的边界澄清）。
- **QQ 号成为整个账号体系的单点** —— 失去 QQ 号即失去账号（见 Q32）。

**双端内容同步（第 13 轮）**：网站内容与 QQ 群内容采用**手动同步** —— 你发一条公告，需在网站与 QQ 群**各发一次**。

| 项目 | 结论 |
| --- | --- |
| 同步方式 | **手动双发**，不建自动同步机制 |
| 对机器人的影响 | 机器人**不需要**任何群消息推送能力，[D-07](#d-07-qq-机器人职责范围限于注册与绑定)、[D-14](#d-14-机器人职责扩展为账号身份锚点) 的"不做通知推送"边界**继续有效** |
| 代价 | 每次发布多一步手工操作；这是**明确接受**的代价 |

**一致性说明**：本条不推翻 [D-01](#d-01-身份与准入qq-群是唯一入口网站不做成员名单校验) —— 网站依然不核对"谁在群里"，只是新增了"证明你是这个账号的主人"这一能力。

## D-15 密码重置为纯对话式流程，无额外校验

**决策**：重置流程完全在 QQ 私聊内以对话完成。

| 步骤 | 行为 |
| --- | --- |
| 1 | 用户私聊发送指令"**重置密码**" |
| 2 | 机器人回复"**请输入新密码**" |
| 3 | 用户发送新密码 |
| 4 | 结束，密码已更新 |

**明确不做的**：

| 不做 | 说明 |
| --- | --- |
| 不做额外身份校验 | 不要求提供学号、姓名或原密码 —— **仅凭 QQ 号身份即可重置** |
| 不做频率限制 | 可反复重置 |
| 不做确认与二次输入 | 无需再次输入以确认 |
| 不做登录态失效处理 | 其他设备上的会话不受影响 |

**备选与取舍**：
- 增加校验（学号 / 原密码 / 二次输入）→ 更安全，但增加对话轮次，且与"用户本来就忘了密码"的场景冲突。
- **最简对话式**（采纳）→ 轮次最少，且与 [D-16](#d-16-保留管理员人工兜底通道) 的人工通道形成互补：输错了也能找管理员救回。

**对架构的影响**：
- 重置不需要网页界面 —— **不存在"重置密码页面"**。
- 机器人需要维护一段**对话状态**（等待用户输入新密码），这是机器人侧唯一的会话状态。
- QQ 号成为账号安全的**唯一凭据**（[D-14](#d-14-机器人职责扩展为账号身份锚点) 已确认此定位）。

### ⚠️ 明确接受的风险

| 风险 | 后果 | 说明 |
| --- | --- | --- |
| **新密码明文经过 QQ 聊天通道** | 密码会留在 QQ 聊天记录中（可能被同步、备份、他人查看） | 由"纯对话式"设计直接导致，无法回避 |
| **任意人可通过 QQ 重置** | QQ 号被盗 = 网站账号被夺 | 已在 [D-14](#d-14-机器人职责扩展为账号身份锚点) 确认为可接受 |
| **无二次确认，输错即锁死** | 用户打错新密码后会立即无法登录 | 由 [D-16](#d-16-保留管理员人工兜底通道) 兜底 |
| **可被反复重置** | 无频率限制 | 无明确滥用动机，接受 |

## D-16 保留管理员人工兜底通道

**决策**：为账号体系保留一条**管理员人工处理通道**，作为自动流程失效时的最终兜底。

**已明确的兜底场景**：

| 场景 | 说明 |
| --- | --- |
| QQ 死局 | 用户 QQ 号被盗 / 停用 / 更换，且无法通过机器人重置 |
| 重置失误 | 用户重置时输错新密码导致锁死（[D-15](#d-15-密码重置为纯对话式流程无额外校验) 无二次确认） |

**备选与取舍**：
- 完全不设人工通道 → 保持"零人工介入"原则的纯粹性，但会产生永久失联的账号。
- **保留人工兜底**（采纳）→ 承认自动化流程有失效边界，用最低成本的人工介入兜住极少数死局。

**对架构的影响**：
- 这是本项目**唯一一处主动引入的人工介入**，与其余"免审批、免审核、免核验"的减负取向形成对照 —— 属于**有意识的例外**，而非原则被打破。
- 需要存在一个**管理员身份**，并具备重置用户密码 / 换绑账号的权限 → 权限模型中的"管理员"不再是虚设。
- 管理员**同时**是公告与活动的发布者（[D-03](#d-03-官方活动与约球为两条独立业务线)），因此"管理员"是一个真实存在、需要被实现的角色。

### 权限模型（第 13 轮补充）

| 角色 | 产生方式 | 能力 |
| --- | --- | --- |
| **超级管理员** | **预先指定**（[D-23](#d-23-超级管理员预先指定不靠注册顺序自动产生)），唯一一个，**可共用** | 全部权力，包括设置管理员 |
| **管理员** | 由超级管理员设置 | 发布公告与活动、账号人工兜底 |
| 成员 | 注册产生 | 服务区全部成员功能 |

**关键性质**：超级管理员**唯一且可共用** —— 即多人可持同一超级管理员账号，而不是各自持有独立账号。

**对架构的影响**：
- 系统需要记录"谁是超级管理员"（唯一标记），而非仅记录"谁是管理员"。
- "设置管理员"是超级管理员的专属能力 → 权限模型存在**两级管理权限**，不是平级的。
- ~~默认首个账号~~ → **已明确为预先指定**（[D-23](#d-23-超级管理员预先指定不靠注册顺序自动产生)），**无抢注风险**。

**待明确**：人工通道是否需要记录操作痕迹（账号共用会影响可追溯性 —— 见 Q41）；超管账号如何转让或新增。

### 与 [D-12](#d-12-注册采用机器人发放邀请码--网页填表的两段式流程) 的联动要求

人工兜底需要管理员能够**修改他人的账号凭据**（换绑 QQ 号 / 代设密码），否则无法处理两类死局。这意味着：

| 要求 | 说明 |
| --- | --- |
| 凭据可被管理员修改 | 账号的 QQ 号与密码对管理员**可写**，而非仅用户本人可写 |
| 管理员身份可核验 | 管理员登录后需被识别为管理员（权限模型中的第三层） |

> 这条与 [D-11](#d-11-账号凭据支持自助换绑) 不冲突：用户自助换绑是常态，管理员修改是例外通道。**因此"账号凭据"在设计上是可写的字段，不是不可变的身份锚点** —— 这一点会影响 P2 的数据模型。

## D-17 机器人采用第三方框架，身份锚点为真实 QQ 号

**决策**：机器人通过**第三方 QQ 机器人框架**实现（非 QQ 官方机器人平台）。身份锚点为**真实 QQ 号**。

**背景**：Q33 查证发现，QQ 官方机器人平台在单聊事件中只提供 `user_openid`，**不提供 QQ 号**，且用户无从知晓自己的 OpenID。你选择走第三方框架路线。

**由此成立的能力**：

| 能力 | 说明 |
| --- | --- |
| 获取发起者的真实 QQ 号 | 邀请码绑定的基础 |
| "QQ 号 + 密码"登录 | **得以保留** —— QQ 号对用户可见，可作登录标识 |
| 一处标识贯穿四用 | QQ 号同时作为：绑定凭据、登录标识、注册页带入项、密码重置的核验依据 |

**备选与取舍**：

| | 官方平台（未采用） | 第三方框架（采纳） |
| --- | --- | --- |
| 身份标识 | OpenID（用户不可见） | 真实 QQ 号 |
| 登录方式 | 只能学号 + 密码 | 学号或 QQ 号 + 密码 |
| 稳定性 | 官方支持 | **灰色地带** |
| 账号风险 | 无 | **你提供的账号可能被封** |
| 申请门槛 | 需注册开发者并过审 | 无门槛 |

**对架构的影响**：
- [D-12](#d-12-注册采用机器人发放邀请码--网页填表的两段式流程)、[D-13](#d-13-邀请码与-qq-号一次性永久绑定不设有效期)、[D-15](#d-15-密码重置为纯对话式流程无额外校验) 三条的"QQ 号"表述**全部成立，无需改动**。
- QQ 号在系统中承担**四重角色**（绑定凭据 / 登录标识 / 注册带入 / 重置核验），是账号体系的核心字段。
- 账号安全模型中，**QQ 号本身不构成秘密**（它半公开、可枚举），真正的秘密只有密码。这与学号作登录名的情形一致，可接受。

### ⚠️ 明确接受的风险：机器人账号被封

**这是全项目风险等级最高的一项**，因为机器人是**唯一的准入门**（[R8](scope.md)）。账号一旦被封：

| 失效的能力 | 后果 |
| --- | --- |
| 签发新邀请码 | **新人完全无法注册** —— 不是体验变差，是功能归零 |
| 重置密码 | 忘记密码的成员无法自助找回 |

**风险等级**：高于 [D-16](#d-16-保留管理员人工兜底通道) 处理的两类死局，因为它的影响面是**全体潜在新成员**，而非个别用户。

### Q36 的答复：不设任何兜底（第 11 轮）

| 问题 | 你的答复 |
| --- | --- |
| 是否准备备用 QQ 账号？ | **无须备用** |
| 是否保留"机器人不可用时的注册兜底通道"？ | **不保留** |
| 迁移到新账号的代价？ | **不大** |

**明确接受的后果**：**机器人账号被封 → 注册与密码重置完全停摆**，直到换上新账号。没有第二条路径。

**你接受此风险的合理依据**：迁移成本低，因此"事后快速恢复"替代了"事前建兜底"。这是一个成立的取舍 —— 前提是迁移确实够快（见下方迁移流程要求）。

**换号迁移的流程要求（本条衍生）**：

| 步骤 | 说明 |
| --- | --- |
| 1 | 准备一个新的 QQ 账号，接入同一套机器人逻辑 |
| 2 | 将新账号拉入社团群 |
| 3 | 新账号此后签发的邀请码绑定**新的 QQ 号** |

**⚠️ 需明确的边界（见 [Q37](open-questions.md)）**：换号后，**用旧账号取得但尚未使用的邀请码**如何处理？若仍可注册，会与 [D-18](#d-18-qq-号注册状态为长期约束不因换号重置) 的"一个 QQ 号只能注册一次"冲突。

## D-18 QQ 号注册状态为长期约束，不因换号重置

**决策**：**QQ 号与账号的对应关系是长期的** —— 一个 QQ 号一旦注册过，此后不得再注册第二个账号。此约束**不因机器人更换账号而重置**。

**背景**：你选择了[不设任何兜底](#q36-的答复不设任何兜底第-11-轮)，机器人账号被封时直接换新账号。这引出一个必须明确的边界：

> 换了机器人账号之后，**已注册过的 QQ 号还算"已注册"吗？**

**答案：算。** 理由：

| 理由 | 说明 |
| --- | --- |
| 机器人账号与用户账号是两回事 | 被封的是**机器人**，用户的账号、积分、对局记录都在网站侧，与机器人账号无关 |
| 否则会开一个后门 | 若换号后重置状态，则任何已注册者都能再注册一个新账号 —— 直接破坏 [D-13](#d-13-邀请码与-qq-号一次性永久绑定不设有效期) 的"一码一 QQ" |
| 与 [D-08](#d-08-注册在-qq-内完成所有权一次性交割给网站) 一致 | 注册完成后所有权归网站，判定依据是**网站侧的数据**，不依赖机器人当前状态 |

**对架构的影响**：
- "某个 QQ 号是否已注册"这个判断的**依据在网站侧**，机器人只是查询方 → 机器人与网站之间必然存在一次**状态查询交互**（见 [Q37](open-questions.md)）。
- 机器人换号是**运维事件**，不是数据事件 —— **不需要任何数据迁移**。这也印证了你判断的"迁移代价不大"。

**已明确（第 12 轮）：未使用的邀请码不作废。**

**决策**：机器人换号后，换号前已签发但尚未使用的邀请码**继续有效**。

**理由**：

| 理由 | 说明 |
| --- | --- |
| 邀请码绑定的是**用户 QQ 号**，不是机器人账号 | 机器人换号不改变任何用户身份，邀请码与 QQ 号的对应关系依然成立 |
| 不作废不产生重复注册风险 | 一个 QQ 号仍只能注册一次（[D-18](#d-18-qq-号注册状态为长期约束不因换号重置)），邀请码继续有效不会开新口子 |
| 避免用户反复申领 | 用户拿到的码不会突然失效，体验更稳 |
| 与数据归属一致 | 邀请码存于网站侧（[D-19](#d-19-邀请码与注册状态数据由网站侧持有机器人是薄客户端)），机器人换号不影响其有效性 |

**待明确**：~~换号前已签发但未使用的邀请码如何处理~~ → **已明确：不作废**。

## D-19 数据由网站侧持有，机器人不持有独立业务数据（访问方式已修订为直连数据库）

**决策**：机器人运行所需的全部业务数据 —— **邀请码、QQ 号注册状态、密码重置的对话状态** —— 均**存放在同一数据源**。机器人不持有**独立的**业务数据。

**访问方式（第 27 轮）**：机器人**直连数据库**读写，不经由网站 API。

> ⚠️ **诚实的修正**：第 12 轮把机器人描述为"**无状态薄客户端**"。改为直连数据库后，这个描述**不再准确** —— 机器人虽仍不持有**独立数据**，但它**承担了业务逻辑**（邀请码生成、按 QQ 号去重、密码写入）。下文保留了对两种方式的完整对比，但**结论已按直连数据库修订**。

**数据归属对照**：

| 数据 | 存放位置 | 机器人做什么 |
| --- | --- | --- |
| 邀请码及其绑定的 QQ 号 | **网站侧** | 收到"注册"后向网站查询／请求生成 |
| 某 QQ 号是否已注册 | **网站侧** | 向网站查询 |
| 重置密码的对话状态（等待输入新密码） | **网站侧** | 转发消息、回传结果 |
| 收发私聊消息、读取发送者 QQ 号 | 机器人侧 | 平台能力 |

**备选与取舍**：

| | 数据存机器人侧（未采用） | 数据存网站侧（采纳） |
| --- | --- | --- |
| 数据源数量 | 两处，需互相同步 | **一处**，网站是唯一权威 |
| 机器人换号的影响 | **数据随账号迁移**，需处理迁移 | **无影响**，换号只是换个前端 |
| 模块边界 | 模糊、双向依赖 | 清晰、**单向依赖** |
| 机器人的复杂度 | 需自持存储与状态 | 薄客户端，几乎无状态 |

**对架构的影响**：

- **架构变为严格单向依赖**：

```
QQ 用户 ──私聊──▶ 机器人（薄客户端，无业务数据）
                      │
                      │ 查询 / 请求
                      ▼
                网站（唯一数据源与业务逻辑）
```

- **机器人不持有独立业务数据** —— 数据仍集中在同一处，因此**机器人换号依然不需要迁移数据**（[D-17](#d-17-机器人采用第三方框架身份锚点为真实-qq-号) 的"迁移代价不大"判断仍然成立）。
- ⚠️ **但机器人不再是无状态的** —— 它直接读写数据，因此**承担了业务逻辑**（邀请码生成、去重、密码写入）。J 模块的定位从"受控接口"变为"**共享数据层的另一个写入方**"。
- 这削弱了 [D-19](#d-19-邀请码与注册状态数据由网站侧持有机器人是薄客户端) 原本"薄客户端"的说法，需要如实记录（见下方"决策修正说明"）。

### ⚠️ 由此产生的安全要求

网站为机器人开放的这些能力 —— 尤其**"按 QQ 号查询是否已注册"**和**"重置任意用户的密码"** —— 一旦被外部直接调用，等于账号体系失守。

| 要求 | 说明 |
| --- | --- |
| 仅机器人可调用 | 这组能力**不得对普通网页访问者开放** |
| 调用方身份需可验证 | 网站需能确认请求确实来自本社团的机器人 |

> 这是 [D-15](#d-15-密码重置为纯对话式流程无额外校验) "重置无任何校验"能够成立的前提：**校验的缺失，由"只有机器人能发起"来兜底**。否则任何人只要能调用该接口，就能重置任意账号的密码。

### 访问机制：**直连数据库**（第 27 轮定案）

**决策**：机器人**直接读写数据库**，网站不为机器人单独开放 API。

> 你在第 26 轮提出，第 27 轮确认。这取代了本条原有"需要暴露一组受控能力"的描述 —— 但 [D-19](#d-19-邀请码与注册状态数据由网站侧持有机器人是薄客户端) 的**核心结论不变**：数据仍全部在**网站侧/同一数据源**，机器人不持有自己的业务数据。

**两种机制的对比**：

| | 甲：API（网站暴露受控能力） | **乙：直读数据库（采纳）** |
| --- | --- | --- |
| 实现速度 | 需要先写接口 | **更快**（直接写查询） |
| 表结构变更的影响 | 不影响机器人 | **机器人的查询会被破坏** ⚠️ |
| 谁能写 | 网站统一校验 | **机器人可绕过网站直接改数据** ⚠️ |
| 密码处理 | 网站负责加密存储 | **机器人需自行正确处理** ⚠️ |
| 业务校验 | 集中在网站 | **分散到两处，需各写一遍** ⚠️ |
| 权限收口 | 只需保护 API 凭据 | 需为机器人建**受限数据库账号** |
| 采纳 | — | ✅ **第 27 轮确认** |

**⚠️ 但有一点必须澄清：机器人用的是同一个数据库，不等于它是"薄"的**

| 项目 | 影响 |
| --- | --- |
| 数据归属 | ✅ 仍是单一数据源，[D-19](#d-19-邀请码与注册状态数据由网站侧持有机器人是薄客户端) 的核心优势（换号不需迁移）**保持** |
| 业务逻辑 | ⚠️ 机器人需要**自行实现**邀请码生成、去重判断、密码写入等逻辑，网站无法代为校验 |
| 表结构 | ⚠️ 成为**双方共同遵守的约定**，改表需同步改机器人 |

**因此，必须满足的最低要求**：

| 要求 | 说明 |
| --- | --- |
| **专用数据库账号** | 绝不能用管理员账号；只授予必需的表与操作 |
| **密码写入规则统一** | 机器人写密码时，必须使用与网站**完全一致的加密方式** |
| **表结构视为约定** | 网站改表时必须同步改机器人，属于额外维护负担 |
| **唯一性约束仍在数据库层** | 如"一个 QQ 号只能注册一次"应靠约束保证，而非靠机器人正确判断 |

**⚠️ 需要注意的一点**：无论选哪种机制，**D-15 的"重置密码无任何校验"始终成立** —— 因为其安全性来自"**只有机器人能发起**"，而不是来自访问方式。若机器人直读数据库，则"能连上数据库"就成了重置任意密码的能力，**凭据保管的重要性不会降低，只会更集中**。

**待你决定**（[Q57](open-questions.md)）。

### ⚠️ 名次制与等级分制不可兼得（第 23 轮结论）

| | 名次制（已放弃） | **等级分制（现行）** |
| --- | --- | --- |
| 结算单位 | 一整场比赛 | **一场对局** |
| 依据 | 最终名次 | **双方胜负** |
| 需要的数据 | 名次（1 个数字） | **每场的对手与胜负** |
| 能否算出"低胜高多得分" | **不能** | 能 |

**⚠️ 等级分制需要逐场对局数据，而"只录名次"提供不了。**

**因此"录入名次"这一形态不成立，需要改为逐场录入对局结果** —— 见 [Q54](open-questions.md)。

**由此产生的录入成本问题**：一场 16 人的比赛若逐场录入，可能是十几到几十条记录；而录入名次只需 1 条。这是等级分制的代价，需要明确接受或寻找折中。

| 新手 | 200–400 |
| 熟手 | 400–600 |
| 高手 | 600–800 |
| 大师 | 800–1000 |

**档位的作用范围（第 14 轮明确）**：档位**仅作为定初始积分时的参考**，此后**不跟随展示**。

| 项目 | 结论 |
| --- | --- |
| 出现时机 | **仅注册后选择自评分时** |
| 是否长期展示 | **不展示**，不随积分变化 |
| 是否用于换算长期标签 | **不适用** |
| 是否必须等宽 | 仍待确认（[Q21](open-questions.md)），但影响面已大幅缩小 |

> 由此，原"积分超过 1000 后档位如何算"的问题**自动消失**（[Q39](open-questions.md) 关闭）。

**备选与取舍**：
- 精确分数 + 档位标签并存 → 兼顾"有具体数字"与"低门槛理解"，但**两套表述可能冲突**；
- 只显示档位 → 更简单，但排行榜失去区分度。

**对架构的影响**：
- 积分与档位是**两个概念**：积分是连续量，档位是**派生标签**（由积分换算）。因此档位**不需要单独存储**，按规则换算即可。
- 注册流程需要**多一步引导**（与 [D-12](#d-12-注册采用机器人发放邀请码--网页填表的两段式流程) 的注册表单分离）。

## D-22 积分分为两个独立量：个人自评分与比赛积分

**决策**：系统中存在**两个互相独立的积分量**，含义与来源完全不同。

| | **个人自评分** | **比赛积分** |
| --- | --- | --- |
| 来源 | **用户自报**（自我评定） | **仅官方比赛**结果产生（[D-20](#d-20-活动报名采用开球网式比赛报名模式)） |
| 性质 | 主观、声明性 | 客观、累积性 |
| 初始值 | 注册后引导选择（**0–1000**，五档话术） | **一律 500** |
| 是否变化 | **不随比赛变化** | 随官方比赛结果持续结算 |
| 能否修改 | **可随时在个人主页自行修改**（第 15 轮） | 不可手工修改 |
| 用途 | 约球时的水平参考 | 排行与竞技记录 |
| 可见位置 | 个人主页 + **约球相关界面（供他人参考）**；**不进排行榜** | **排行榜**（唯一排名依据） |
| 档位标签 | 五档（小白→大师）**仅用于选择自评分时参考**，不跟随 | 不适用 |

**备选与取舍**：
- 单一积分（原设计）→ 简单，但"自我声明"与"实际战绩"混在一起，语义不清。
- **拆为两个量**（采纳）→ 语义清晰：自评分表达"我认为我是什么水平"，比赛积分表达"我打出来的成绩"。两者不互相覆盖。

**对架构的影响**：
- 用户档案上需要**两个积分字段**，而非一个。
- 排行榜将面临一个必须解决的问题：**展示哪一个，还是两个都展示？**（见 [Q42](open-questions.md)）
- [D-09](#d-09-积分体系规则自报初始分不重置单双合并) 的结算规则（单双打、平均分、算胜负、不重置）适用于**比赛积分**；自评分不参与结算。

**档位标签的性质（第 13 轮明确）**：五档**仅在注册选择自评分时出现**，此后不再跟随展示。因此：
- 不存在"积分超过 1000 后档位怎么算"的问题（原 [Q21](open-questions.md) 第 3 点、[Q39](open-questions.md) 由此关闭）；
- 档位是**一次性选择工具**，不是长期标签。

### 榜单与可见性（第 15 轮明确）

| 项目 | 结论 |
| --- | --- |
| 排行榜展示 | **只展示比赛积分**（方案 B）—— 不存在自评分榜 |
| 自评分可见位置 | 个人主页 + **约球相关界面**（供约球者参考） |
| 自评分修改 | 个人主页**随时可改**，不限制次数 |

```
自评分（0–1000，自报，可随时改）
   └─ 展示于：个人主页、约球界面        └─ 不进排行榜

比赛积分（起 500，仅官方比赛结算）
   └─ 展示于：排行榜                 └─ 唯一排名依据
```

**对架构的影响**：
- 排行榜页结构**简化**：只有一个榜（比赛积分），不需要合并或切换两个榜。
- 因为 [D-09](#d-09-积分体系规则自报初始分不重置单双合并) 限定比赛积分**仅由官方比赛产生**，所以参加官方比赛是**提升比赛积分的唯一途径** —— 排行榜实际反映的是"谁参加了比赛、打得如何"。
- 自评分是**可随时刷新的声明**，参考价值随时间与动机波动；这是"仅供参考"定位的直接结果。

**待明确**：
1. 比赛积分的**上下限**规则（起 500，是否设顶 / 底？）—— [Q45](open-questions.md)
2. 官方比赛如何组织**单打与双打**（[D-09](#d-09-积分体系规则自报初始分不重置单双合并) 原定单双都支持）—— [Q45](open-questions.md)
3. 排行榜的**场次 / 胜率**统计是否包含日常对局 —— [Q44](open-questions.md)

## D-23 超级管理员预先指定，不靠注册顺序自动产生

**决策**：超级管理员由**预先指定**产生，**不采用**"第一个注册的账号自动成为超管"这一自动规则。

**备选与取舍**：

## D-24 自评分对约球者可见，且可随时自行修改

**决策**：

| 项目 | 结论 |
| --- | --- |
| 可见位置 | 个人主页 + **约球相关界面**（供约球者参考水平） |
| 修改权限 | 用户**在个人主页随时自行修改**，**不限制次数** |
| 是否进排行榜 | **否** |

**备选与取舍**：
- 自评分不可改 → 初学者水平提升后无法更新，声明会长期失真；
- 限制修改频率（如每学期一次）→ 更稳定，但需要额外的限制逻辑；
- **完全自由修改**（采纳）→ 实现最简单，与"仅供参考"的定位自洽。

**明确接受的后果**：
- 自评分是**完全可刷新的声明**，参考价值取决于成员的诚实程度；
- 由于 [D-06](#d-06-账号采用学号--qq-号双绑定学号仅作标识) 已确认账号唯一性**无技术保证**，本项也不做防滥用设计 —— 与全局"自律优先"的取向一致。

**对架构的影响**：
- 个人主页需要"修改自评分"入口。
- **约球界面需要展示发起者与参与者的自评分** → 约球模块与用户档案之间存在数据依赖（但不涉及权限校验，仅展示）。

## D-25 赛季为一级实体，按学期自动归档

**决策**：引入**赛季**作为系统中的一级实体。按**学期**自动开启新赛季，旧赛季**归档保留**。

| 项目 | 规则 |
| --- | --- |
| 赛季粒度 | ✅ **一赛季 = 一学年**（第 20 轮确认，[Q49](open-questions.md) 关闭） |
| 赛季命名 | **`2025/2026`** 格式 |
| 触发 | **自动**；**两学期的起止日期由管理员配置** |
| 归档时刻 | **学年结束当天归档**（即春季学期最后一天） |
| 休赛期 | **寒暑假不开展活动**，为休赛期 |
| 归档方式 | **乙式**：旧赛季积分与对局记录**完整保留** |
| 历史可见 | **需要** —— 用户能查看往期赛季 |
| 新成员初始值 | 每个赛季**仍为 500** |
| 对自评分的影响 | **无**（两者独立，[D-22](#d-22-积分分为两个独立量个人自评分与比赛积分)） |

**备选与取舍**：

| | 甲：清零归位（未采用） | 乙：赛季归档（采纳） |
| --- | --- | --- |
| 历史 | 全部作废 | **完整保留** |
| 数据模型 | 一个数字字段 | **需要赛季维度 + 归档** |
| 工作量 | 小 | **明显更大** |
| 价值 | 每学期重新开始 | **可对比历届成绩、可追溯** |

**对架构的影响**：

| 影响面 | 说明 |
| --- | --- |
| 新增实体 | **赛季**（起止时间、名称） |
| 对局记录 | 必须**归属到具体赛季** |
| 积分 | 从"单一数字"变为"**每赛季一份**" |
| 排行榜 | 默认当前赛季，需支持**切换历史赛季** |
| 成员档案 | 可能需要展示"历史赛季成绩" |

### 时间规则（第 18 轮）

| 项目 | 结论 |
| --- | --- |
| 学期起止 | **由管理员配置**（不是硬编码，管理员可设定每学期的开始与结束日） |
| 自动动作 | 按配置的时间**自动归档** |
| 归档时刻 | **学期结束当天** |
| 寒暑假 | **休赛期** —— 不开展**官方活动**（约球**不受限制**，见 [D-03](#d-03-官方活动与约球为两条独立业务线)） |
| 赛季命名 | `2025/2026` 这种格式 |

**"管理员配置 + 系统自动执行"是一个好组合**：时间边界由你按学校实际校历录入，归档动作由系统执行 —— 你不需要记得在某个日子点按钮，但也不必把校历写死在系统里。

### 起止日期的配置与容错（第 19 轮）

| 情况 | 规则 |
| --- | --- |
| 未配置新学期日期 | **沿用上学期**的起止日期 |
| 中途修改起止日期 | **已产生的对局仍然有效**，不追溯调整 |

**"沿用上学期"的含义**：系统不会因为缺配置而停摆，而是按上一次的日期继续推算 —— 保证赛季仍会自动归档；代价是日期可能与实际校历有偏差，**需要你及时更新**。

**"已产生对局仍有效"的含义**：修改配置**不是**重写历史的操作，而是**只影响尚未发生的部分**。这避免了"改一个日期导致一批对局归属变化"的连锁问题。

### 赛季粒度定案（第 20 轮）

**一赛季 = 一学年**（[Q49](open-questions.md) 关闭）。

这也**解释了此前两处看似不一致的表述** —— 它们说的其实是同一件事：

| 表述 | 出处 | 现在如何理解 |
| --- | --- | --- |
| "按**学期**自动执行" | 第 17 轮 | 指**学期的起止日期**由你配置；自动动作按这些节点走 |
| "结束当天归档" | 第 18 轮 | 指**学年结束当天**（春季学期最后一天）归档 |

**一个学年的结构**：

```
2026/2027 赛季  ═══════════════════════════════════════
  秋季学期           寒假        春季学期         暑假
 （活动+积分）    （休赛期）   （活动+积分）    （休赛期）
                                              ▲
                                         学年结束当天
                                           自动归档
```

| 阶段 | 官方活动 | 积分 |
| --- | --- | --- |
| 秋季学期 | 开展 | 累积 |
| 寒假 | **休赛期** | 停止 |
| 春季学期 | 开展 | 累积（接续秋季） |
| 暑假 | **休赛期** | 停止；**学年结束 → 归档** |

### ⚠️ 顺带产生的公平性问题（需你确认）

因**一赛季 = 一学年**，而比赛积分起始值固定为 **500**，新成员若在**学年中途**加入：

| 情况 | 后果 |
| --- | --- |
| 秋季加入 | 有完整两学期累积积分的机会 |
| **春季（或更晚）加入** | 只有半个学年，**起点 500 但场次少** → 排名天然偏低 |

**这可能不是问题**（排行榜本就反映实际战绩），但需要你确认是**有意的**。若希望缓解，可选做法（仅供参考，未决）：

| 可选做法 | 说明 |
| --- | --- |
| 不处理 | 认可排行榜反映参与度与战绩（**最简单**） |
| 按场次设最低门槛 | 场次不足者单独列出或不参与排名 |
| 展示"场均积分变化" | 用比率而非绝对值，对新成员更公平 |

**见 [Q50](open-questions.md)**。

**待明确**：新生排名公平性（[Q50](open-questions.md)）。赛季的**时间规则**已完整。

## D-27 管理权限的边界与操作留痕（Q41 的答复）

**背景**：[D-16](#d-16-保留管理员人工兜底通道) 确立了两级管理权限（超管设置管理员），但留了 [Q41](open-questions.md) 未答。三个问题在第 44 轮得到答复。

### 答复一：账号共用导致操作无法追溯到具体的人 —— **可以接受**

**决策**：超管账号保持**可共用**（[D-16](#d-16-保留管理员人工兜底通道) 的原始约定不变），不引入「一人一超管账号」的改造。

**已接受的后果**：操作记录只能记到**账号**粒度，无法知道是哪位成员在操作。

### 答复二：管理员的账号形态 —— **独立账号**

**决策**：管理员**各自持有独立账号、各自登录**，不与超管账号共用。

**含义**：

| 角色 | 账号形态 |
| --- | --- |
| 超级管理员 | **唯一账号、可多人共用** |
| 管理员 | **每人独立账号**（由超管在自己的账号里设置） |
| 成员 | 每人独立账号（注册产生） |

**这带来一个正面效果**：管理员的**操作是可追溯的** —— 因为他们各自登录，操作记录里的账号就等于具体的人。**只有超管这一层是模糊的**，而超管本来就是信任度最高的一层。

### 答复三：是否需要「管理员不得操作超管账号」这类边界 —— **需要**

**决策**：设置**管理员不得操作超管账号**的边界。

**已实现的边界**（与角色管理一并上线）：

| 边界 | 理由 |
| --- | --- |
| 只有超管能设置/取消管理员 | [D-16](#d-16-保留管理员人工兜底通道)：设置管理员是超管专属能力 |
| 管理员**看不到也进不了**「成员与权限」页 | 入口与页面双重限制 |
| 超管账号的角色**不可被修改** | 超管由预先指定产生（[D-23](#d-23-超级管理员预先指定不靠注册顺序自动产生)），转让/新增仍是未决问题 |
| 不能修改自己的角色 | 防止超管误降级自己，导致**再无人能设置管理员**（死锁） |
| 接口层独立鉴权 | 只隐藏入口不够：实测普通成员构造请求会被拒 |

**尚未实现但已定的边界**（待对应功能出现时落实）：

| 边界 | 出现时机 |
| --- | --- |
| 管理员**不得代超管账号重置密码 / 换绑** | 待 [D-16](#d-16-保留管理员人工兜底通道) 的「账号人工兜底」功能实现时 |

### D-27 附：操作留痕的实现

**决策**：新增 `audit_logs` 表，记录管理动作。

**记录内容**：`actor_user_id`（谁）、`actor_name`（**姓名快照**）、`action`（做了什么）、`detail`（对谁/什么）、`created_at`（何时）。

**两个设计取舍**：

| 取舍 | 理由 |
| --- | --- |
| `actor_name` 存**快照**而非靠 JOIN 取 | 账号改名或删除后，历史记录仍应显示当时的名字；靠 JOIN 会让历史随账号变动而失真 |
| 写日志**失败不影响主流程** | 若审计写入失败导致「设置管理员」失败，是本末倒置。故内部吞掉异常并打日志 |

**已覆盖的动作**：`role.grant`、`role.revoke`、`announcement.create`、`announcement.update`、`announcement.delete`。
**查看入口**：`/admin/audit`（仅超管可见）。

**同时引入的东西**：项目此前**没有数据库迁移机制** —— `schema.sql` 只在数据卷为空时执行一次，一旦有了真实数据，加表就再也不会自动生效。现新增 `web/scripts/migrate.mjs`：按文件名顺序执行 `web/db/migrations/*.sql`，每个文件在独立事务中运行，已执行的记入 `schema_migrations`。

## D-28 活动模块的四个细节（第 57 轮）

**背景**：[D-20](#d-20-活动报名采用开球网式比赛报名模式) 定了活动报名的骨架（名额单位、候补、搭档双向确认、签到），但留了四个细节未定。本轮逐条敲定。

### 一、候补递补：**自动**

**决策**：有人取消 → 按 `registered_at` 顺序把**最早的候补自动转为正式**，无需管理员操作。

**理由**：与项目整体的「减少人工介入」取向一致（[R-12](requirements.md) 单人维护）。若靠管理员手动递补，取消后名额会空着等人处理。

### 二、双打中一人取消：**整队释放，队友需重新登记**

**决策**：双打队伍中任一成员取消 → **整个队伍的名额立即释放**给候补；队友被告知，**需重新报名**（可另找搭档）。

**理由**：名额单位是**队**（[D-20](#d-20-活动报名采用开球网式比赛报名模式)），半支队不构成一个名额。保留半队会让「名额 = 一队」这个前提失效。

**明确接受的代价**：队友被「牵连」——他自己没取消却失去了名额。这是「按队计算名额」的必然结果。

**与「管理员后配」的关系**：后配（[D-20](#d-20-活动报名采用开球网式比赛报名模式)）针对的是**从未配过队的单人报名者**，与本条（已成队后一人退出）是不同场景，二者不冲突。

### 三、未签到者：**标记缺席，无积分后果，但影响候补优先级**（关闭 [Q58](open-questions.md)）

| 子问题 | 结论 |
| --- | --- |
| 是否标记缺席 | **是** |
| 是否有积分后果 | **否**（[D-04](#d-04-积分定位为参考性荣誉系统) 已定积分只由比赛产生） |
| 是否影响后续报名 | **是** —— 名额已满时，**有缺席记录者排在无缺席者之后** |
| 管理员能否事后补签 | **能** |

**关于第三条的分量**：这是项目里**唯一的成员信誉机制**。积分体系不惩罚爽约（报名不参加不影响积分），
因此需要一个轻量约束防止「占着名额不来」。

**为什么不是硬性惩罚**：缺席原因是多样的（临时有事、记错时间），硬性禁止报名过于严厉。
排序靠后是**软约束**：名额不紧张时完全无影响，紧张时让位给更可能到场的人。

**实现方式**：新增 `absent` 状态（迁移 004）。原设计只用 `checked_in_at IS NULL` 表示未签到，
无法区分「活动还没开始」与「活动结束了但没来」——那是两种完全不同的含义。

### 四、报名截止：**可配置，默认赛前 24 小时**

| 项目 | 结论 |
| --- | --- |
| 默认值 | 赛前 **24 小时**（沿用项目的「24 小时」节奏，见 [D-20](#d-20-活动报名采用开球网式比赛报名模式)） |
| 是否可改 | **可** —— `events.registration_deadline` 字段已存在，管理员发布时填写 |
| 截止后 | **不能报名、不能取消** |
| 截止后需增删人员 | 由**管理员手动处理**（[D-16](#d-16-保留管理员人工兜底通道) 的人工兜底通道） |

**与「取消截止赛前 24 小时」的关系**：两者默认值相同，但是**两个独立概念** ——
一个管「还能不能报名」，一个管「还能不能取消」。管理员可以把报名截止设得更早（例如赛前 3 天），
而取消截止仍是赛前 24 小时。

## D-29 约球模块的四个收尾分支（第 59 轮）

**背景**：[D-10](#d-10-约球房间的字段与生命周期) 定义了房间字段与生命周期，但留了 Q23 / Q24 的收尾分支未定。本轮敲定。

### 一、提供「我的约球」视图：**需要**

**决策**：新增「我的约球」页，含**我发起的**（含待处理申请队列）与**我加入的**。

**理由**：[D-10](#d-10-约球房间的字段与生命周期) 定了「发起人审批制」，那么发起人必须有一个地方看到申请队列 —— 否则审批无处可做。这不是可选项，是审批制的必要配套。

**同时关闭 [Q23](open-questions.md) 的剩余部分**：「水平要求」等信息一律写在**备注**里（与 [R-55](requirements.md) 不设场地与赛制字段一致）。

### 二、取消房间后：**仅标记已取消，无任何信誉影响**（关闭 [Q24](open-questions.md) 之一）

| 项目 | 结论 |
| --- | --- |
| 房间状态 | 置 `cancelled`，从列表消失 |
| 已加入成员 | 记录保留，能看到房间已取消 |
| 信誉影响 | **无** |
| 通知 | **不做**（项目当前没有站内信系统，且与整体减负取向不符） |

**理由**：约球是「找人一起玩」，临时取消很常见（天气、有课、临时有事）。项目整体是**信任优先**的取向（[D-04](#d-04-积分定位为参考性荣誉系统)、[D-06](#d-06-账号采用学号--qq-号双绑定学号仅作标识) 都不做防滥用设计），此处不引入惩罚。

### 三、无人审批的申请：**随房间 24 小时一起过期**（关闭 [Q24](open-questions.md) 之二）

**决策**：房间过期时，其下所有 `pending` 申请一并转为 `expired`，不单独处理。

**理由**：房间本身就是 24 小时的生命周期（[D-10](#d-10-约球房间的字段与生命周期)），申请在这个窗口内没被处理，随窗口一起结束是最简单的语义。

### 四、过期时已有人加入：**算正常结束**（关闭 [Q24](open-questions.md) 之三）

**决策**：房间状态置 `expired`，已有成员的记录保留。**不区分「约成了」与「没约成」**。

**理由**：是否真的打成了球是线下事实，系统无从判断也不应判断。若强行区分，就需要成员回填结果，而那是已经作废的 [D-05](#d-05-对局采用双方握手确认制无审核) 思路。

**由此确定的房间状态机**（[D-10](#d-10-约球房间的字段与生命周期) 的「双向转换」）：

```
                 满员
  open  ──────────────────▶  full
    │  ◀──────────────────    │
    │      有人退出            │
    │                          │
    ├──── 发起人取消 ────▶ cancelled
    └──── 24h 到期  ─────▶ expired      （full 同样可到期）
```

## D-30 积分模块的三项收尾决定（第 61 轮）

**背景**：[D-09](#d-09-积分体系规则自报初始分单双合并重置条款已修订) 已把结算规则定到「无待明确」（标准 ELO、K=40、零和、双打取平均且同增减），
[D-25](#d-25-赛季为一级实体按学期自动归档) 定了赛季归档。本轮补齐排行榜与纠错三项。

### 一、排行榜的场次公平性：**不做门槛，但显示场次**（关闭 [Q50](open-questions.md)）

**背景**：一赛季 = 一学年，新成员固定起 500。春季才加入者场次少，排名天然偏低。

| 可选做法 | 结论 |
| --- | --- |
| 不处理，但显示场次与胜率 | **采纳** |
| 设最低场次门槛 | 不采纳 |
| 改用「场均积分变化」 | 不采纳 |

**理由**：
- 加门槛会让新人**看不到自己的位置**（体验差），与「让人愿意参与」相悖；
- 显示场次已经足够让读者判断参考价值 —— 800 分是打了 20 场还是 2 场，一眼可辨；
- 与 [D-04](#d-04-积分定位为参考性荣誉系统) 的「仅供参考」定位一致：不追求统计上的绝对公平。

### 二、排行榜功能范围：**分页 + 搜索，不做时间筛选**（关闭 [Q22](open-questions.md)）

| 功能 | 结论 |
| --- | --- |
| 分页 | **要**（每页 50） |
| 搜索（姓名 / 学号） | **要** |
| 按时间段筛选 | **不要** —— 赛季本身就是时间维度，再加月/周筛选意义不大 |
| 展示字段 | 排名、姓名、积分、场次、胜率 |

**已定项重申**：榜上显示**姓名**（[R-54](requirements.md)）；游客**看不到**排行榜（[R-29](requirements.md)）。

### 三、录错了怎么办：**允许撤销，但只能撤销最近一场**

**这是对 [D-09](#d-09-积分体系规则自报初始分单双合并重置条款已修订) 中「不可撤销 + 不可修正」的修订。**

**修订理由**：原判断基于已作废的 [D-05](#d-05-对局采用双方握手确认制无审核)（双方握手确认制）—— 那时有双方把关，
录错概率低。现在改为**管理员独自录入、无第二人复核**（[D-20](#d-20-活动报名采用开球网式比赛报名模式)），出错概率显著上升。

**为什么只能撤销最后一场**：ELO 是**链式**的 —— 每场的期望值取决于**当时的**积分。
撤销中间某场，会让其后所有场次的积分都失去依据，必须整体重算。

| 方案 | 可行性 |
| --- | --- |
| 撤销最后一场 | ✅ 只需回滚该场，并减去各参与者的 `delta` |
| 撤销中间任意场 | ❌ 需要重放其后全部场次；且期间可能有赛季归档，复杂度失控 |
| 完全不可撤销 | 已不适用（见上） |

**附带效果**：撤销本身也会记入操作留痕（[D-27](#d-27-管理权限的边界与操作留痕q41-的答复)）。

### 开发中发现的约束缺口（一并记录）

原 schema 只约束了 `format IN ('singles','doubles')` 与 `side IN ('a','b')`，
**没有任何东西保证「单打每侧 1 人、双打每侧 2 人」**。而「双打取平均」依赖双方各 2 人。
这类跨表计数无法用简单 CHECK 表达，因此在**结算逻辑中强制校验**，作为唯一入口。

## D-31 社团照片的存储与展示（第 71 轮）

**背景**：社团需要展示活动照片。原先项目没有任何图片存储能力（只有 logo 这类静态资源）。
用户提出后逐项敲定。

### 一、存储：**命名卷 + 上传接口**（不用数据库存二进制，也不用对象存储）

**先排除一个错误做法**：照片**不能**放在 `web/public/`。
本项目的部署方式是「本地构建镜像 → `docker save` → 服务器 `docker load`」，
`public/` 里的文件是**打进镜像**的 —— 用户上传的照片会在下次部署时**全部消失**。

| 方案 | 结论 |
| --- | --- |
| **命名卷 + 上传接口** | **采纳** |
| 存进数据库（bytea） | 不采纳：大图会撑大数据库、拖慢备份 |
| 对象存储 / 图床 | 不采纳：需外部账号与费用；本项目规模不需要 CDN |

**理由**：项目已有数据卷机制（`db_data`、`napcat_config` 等），复用同一套概念，
不引入外部依赖，也不产生费用。社团照片数量级（几十到几百张）卷完全够用。

### 二、上传权限：**仅管理员**

**理由**：照片是社团**对外形象**，与公告、活动同级（R-43 / D-16 已把「发布」类能力归给管理员）。

**明确不做的**：成员自由上传。虽然项目整体是「信任优先」取向，
但照片是**公开可见**的对外内容，与约球这类内部自助功能不同，因此保留管理员把关。

### 三、展示位置：**社团介绍页 + 独立相册页 + 首页精选**

| 位置 | 说明 |
| --- | --- |
| **社团介绍页** | 介绍社团本来就该有图，最名正言顺的位置 |
| **相册页 `/gallery`** | 独立页面，按时间倒序浏览全部照片 |
| **首页** | 取相册里标记为「精选」的几张 |

**「精选」标记**：管理员可在后台上传/管理照片时勾选，决定哪些上首页。
这样首页的取舍不必修改代码。

### 四、每张照片配简短说明：**要**

**理由**：没有说明的照片展示价值很低（看的人不知道在看什么）。
说明即为 `caption`，可选填，但界面上会引导填写。

### 五、上传时压缩：**要（客户端压缩）**

| 项目 | 结论 |
| --- | --- |
| 目标 | 长边 ≤ 1920px、JPEG 质量 85 |
| 实现 | **浏览器端 canvas 压缩** |
| 服务端 | 只做校验（大小上限、文件头），不做重新编码 |

**为什么客户端压缩**：手机照片动辄 5–10MB，不压缩会拖慢页面、占满磁盘。
浏览器 canvas 零依赖即可完成，而服务端重新编码需要在容器里装图像库（sharp 等），
会显著增大镜像体积 —— 本项目的部署机磁盘与内存都紧张，不值得。

**绕过的可能性**：只有管理员能上传，不存在恶意用户绕过压缩的动机；
服务端仍保留大小上限作为兜底。

## D-32 组织称谓：「社团」是性质，「协会」是正式名称（第 75 轮）

**背景**：做 favicon 时，我看到 logo 上写的是「匹克球**协会**」，
而文档里一律写「匹克球**社团**」，一度打算把文档统一改成「协会」，
并向用户确认 —— 用户指出两者**不是同一个维度**：

| 词 | 含义 | 用法 |
| --- | --- | --- |
| **社团** | 组织的**性质** —— 校级学生社团 | 描述性表述、说明组织类型时用 |
| **协会** | 组织的**正式名称** | 品牌、logo、网站标题、对外自称 |

**决策**：

| 场景 | 用词 |
| --- | --- |
| 网站品牌、页面标题、logo、对外展示 | **协会**（如「东北林业大学匹克球协会」） |
| 文档中说明「这是一个什么组织」 | **社团**（如「校级学生社团」） |
| 「社团活动」「社团公告」这类**通用词组** | 保留「社团」—— 它们指活动/公告的类别，不是组织自称 |

**为什么值得单独记一条**：这不是措辞偏好，而是**两个不同维度**的词。
把它们当作同义词去「统一」，会把组织的正式名称抹掉。

## D-33 安全整改：会话失效、安全响应头、认证限流（第 78 轮）

**背景**：用户要求做一轮全盘安全 review。逐项实测后发现 3 个可修的问题，用户批准整改。

### 一、改密码后失效既有会话（修订 D-15 的副作用）

**问题**：原先全项目只有一处删除会话 —— 登出。因此**改密码不会踢掉任何已登录设备**。
会话有效期 30 天，意味着密码泄露后即便立刻改密码，攻击者的会话仍然有效。
这同时让 [D-16](#d-16-保留管理员人工兜底通道) 的「管理员代设密码」这个兜底手段**踢不掉已经入侵的人**。

**与 D-15 的冲突与化解**：[D-15](#d-15-密码重置为纯对话式流程无额外校验) 明确「重置密码不失效其他设备的登录态」，
其**初衷**是不让人重置一次密码就在所有设备被迫重新登录。本整改同时满足两者：

| 场景 | 处理 |
| --- | --- |
| 用户自己在个人主页改密码 | 只失效**其他设备**，当前设备保留 |
| 机器人重置密码（QQ 死局） | **全部**失效 |
| 管理员代设密码（人工兜底） | **全部**失效 |

**规则只有一份实现**：机器人通过共享规则接口新增的 `invalidate-sessions` 调用，
不自己删表 —— 与密码加密同理（改密码后该做什么属于账号规则）。

### 二、安全响应头（CSP 用 nonce，不用 unsafe-inline）

**已下发**：`Strict-Transport-Security`、`X-Content-Type-Options`、`X-Frame-Options`、
`Referrer-Policy`、`Permissions-Policy`、`Content-Security-Policy`。

**⚠️ 这里有一段值得记住的教训**：

最初把 CSP 写在 Caddy 里、用 `script-src 'self'`。这**打断了整站交互** ——
Next.js 会内联注入 3 个关键脚本（Turbopack 的 chunk 清单、RSC payload），
它们是 React 水合的前提，被 CSP 拦掉后页面退化成静态 HTML。

我当时用无头浏览器截图发现「轮播不动」，**却误判为工具缺陷**（认为截图不等定时器）——
其实是真实回归。直到检查内联脚本才确认。**教训：当测试结果与预期不符时，
先怀疑被测对象，而不是先怀疑测试工具。**

**正确做法**：由 `web/src/middleware.ts` 生成 nonce，写进**请求头**（Next.js 会读取它，
见 `getScriptNonceFromHeader`，自动给内联脚本加 nonce 属性）与**响应头**。
两者源自同一次生成，因此必然一致。已实测：3 个内联脚本全部带上 nonce，且每次请求的 nonce 不同。

**CSP 只由 web 侧设置**：Caddy 不再设 CSP，否则会覆盖 middleware 的。
其余安全头留在 Caddy（静态，不需要 nonce）。

### 三、认证接口限流

**问题**：实测登录接口原无限流 —— 15 次错误尝试 3 秒完成。
虽有约 200ms 的 scrypt 成本（约 12 次/秒），但对弱密码已足够危险。

**做法**：`web/src/middleware.ts` 按 **IP** 计数（内存 Map，不入库 —— 单实例部署足够）：
登录 10 次/分钟、30 次/小时；注册 20 次/分钟。

| 设计选择 | 理由 |
| --- | --- |
| 按 IP 而非按账号 | 按账号会让攻击者故意输错来**锁死别人的账号** |
| 成功即清零 | 路由处理在登录成功后清除计数，正常用户偶尔输错不受影响 |
| 取不到 IP 时不限流 | fail-open：宁可漏挡，也不要把所有人锁在门外 |
| 内存而非数据库 | 单实例部署；入库会让每次登录多一次写操作 |

**已知局限**：分布式攻击（多 IP）可绕过。本站在校园社团场景下不具针对性攻击价值，故不引入外部存储方案。

### 四、本次 review 确认**无需修**的项

| 项 | 实测证据 |
| --- | --- |
| 外部暴露面 | 数据库/web/bot 均未发布端口；NapCat 绑定 127.0.0.1；仅 80/443/22 对外 |
| 访问控制 | 未认证调用 5 个管理接口全部 303 跳登录；普通成员上传/访问管理页/删他人照片全部被拒 |
| 共享规则接口 | 无 token、错 token 均 401 |
| SQL 注入 | 全部参数化；模板中的 `${}` 均是硬编码列名常量 |
| 密码存储 | scrypt + 随机盐 + 恒定时间比较 + 不存在账号走 DUMMY_HASH 防时序侧信道 |
| 会话 cookie | httpOnly + sameSite=lax + secure + path=/ |
| CSRF | sameSite=lax 阻断跨站 POST；写接口校验 content-type |
| XSS | 无 dangerouslySetInnerHTML、无 eval；React 默认转义 |
| 路径穿越 | 文件名服务端生成（UUID+白名单后缀）+ basename 纵深校验 |
| 文件类型伪造 | 按魔数识别，不信任浏览器 MIME |
| 密钥管理 | .env 未被 git 跟踪（权限 600）；无硬编码凭据 |
| 依赖漏洞 | npm audit：0 vulnerabilities |

**尚未处理**（需用户操作或另行决定）：SSH 允许 root 登录 + 密码认证（需 sudo）；
超管密码仍是初始化时的 `nefupa2026!`。

## D-34 首页文案可编辑：用「键值配置表」而不是每项一张表（第 80 轮）

**需求**：用户提出「hero 页的文本改为可编辑」。

### 一、可编辑的范围：标题与副标题

| 元素 | 是否可编辑 | 理由 |
| --- | --- | --- |
| Hero 大标题 | ✅ | 纯文案 |
| Hero 副标题 | ✅ | 纯文案 |
| Hero 按钮文字 | ❌ | 按钮**随登录状态切换**（未登录显示「注册/登录」，已登录显示「去约球/个人主页」）。做成可配置会立刻与登录逻辑打架 —— 配置了一个「注册」按钮文字，登录后的用户会看到错误的按钮 |

### 二、存储：通用键值表 `site_settings`

**为什么不沿用 `club_pages` 那种「固定行 + slug」**：
`club_pages` 是社团介绍的**四块长文本**，结构固定、每块一个字段，适合固定行。
而首页标题这类是**零散短配置**，且可以预期会陆续增加（页脚说明、公告页顶部提示…）。
若每加一项就建一张表、写一个迁移、做一个页面，成本过高。

**键值表的好处**：新增一项配置 = 加一个键 + 在 `SETTING_DEFS` 里加一行定义，**无需再写迁移**。
「有哪些键」由代码侧维护（`web/src/modules/setting/service.ts` 的 `SETTING_DEFS`），管理页据此渲染表单。

### 三、空值语义：回退到代码里的默认文案

管理员**清空**某项时，页面显示的**不是空白**，而是回退到代码中的默认文案
（`getValue` 在取不到或为空时返回 `fallback`）。

**理由**：把标题清空导致首页出现一块空白，是纯粹的事故。
回退语义让「清空」变成一个**安全的撤销操作**，管理员可以放心试。

### 四、本次同时修正的一个流程缺陷

部署命令原本没有 `set -e`。这次 `npm run build` **构建失败**后脚本仍继续执行，
结果是：**把上一次的旧镜像当成新镜像推到了服务器**，而且迁移用的还是旧镜像里的文件
（因此 012/013 两个迁移根本没跑，日志显示「数据库已是最新」，极具误导性）。

**这是一次静默失败** —— 部署看上去成功了，实际什么都没更新。
现已在部署命令前加 `set -euo pipefail`：**构建失败即中止**。

**教训**：部署流水线里任何一步失败都必须中止后续步骤。
「继续执行」在构建失败时不会带来任何好处，只会制造「看起来成功」的假象。

## D-35 个人主页完善：定位、待办集中、个人简介（第 81 轮）

**背景**：用户提出「完善个人主页」。先做现状盘点，结论是 ——
**功能上其实已经完整**（身份、比赛积分、自评分、凭据换绑、登出都在），
问题在于它**像一张信息表，而不是「我的」入口**。

### 一、定位：个人主页要回答三个问题

成员从 QQ 群点进来，只想知道：

1. **我现在怎么样？** —— 积分、排名、战绩、胜率
2. **有什么等着我做？** —— 待确认搭档、即将参加的活动、待处理的约球申请
3. **我参与过什么？** —— 我报名的活动、我的约球

原先只回答了第 1 个的一半。

### 二、待办集中到一处（本轮的主要结构改动）

把三类**「有事等你做」**的信号合并为一张卡片，**仅在有待办时出现**：

| 来源 | 为什么算待办 |
| --- | --- |
| 待我表态的双打搭档邀请 | 不表态，搭档一直在等 |
| 即将开始的已报名活动 | 提醒时间地点 |
| 我发起且有人申请的约球房间 | 别人在等我的决定 |

**为什么「仅在有内容时出现」**：常驻一个空的「待办（0）」区块只会占版面、制造噪音。

### 三、个人简介（新增）

| 项 | 决定 |
| --- | --- |
| 字段 | `users.bio`，上限 **100 字**（应用层校验 + 数据库 CHECK 兜底） |
| 可见范围 | **成员之间可见**，与姓名一致（R-53）；不对外公开 |
| 展示位置 | **目前仅个人主页** |
| 格式 | 单行；换行与连续空白压成空格 |
| 留空 | 允许（可选字段，不强迫填写） |

**关于「成员可见但只在个人主页展示」**：用户选择了可见范围为成员、展示位置为个人主页。
这两者当前并无矛盾 —— `bio` 字段对成员可读，
只是个人主页本身**目前仅本人可访问**（没有 `/members/[id]` 这类公开页）。
因此现阶段没有其他人能看到它；字段的成员可读性是**为后续做准备**。
若将来要在「待确认搭档」等处展示对方简介，不需要改数据结构。

**为什么不给简介加操作记录**：简介不影响他人权益。
每次改动都留痕只会淹没真正重要的记录（对比：改密码、改角色、删内容都留痕，因为那些有实际影响）。

个人主页是否展示它不改变可见性，用户的选择纯粹是产品取向。

## D-36 成员主页：字段白名单与隐私边界（第 90 轮）

**背景**：用户问「如何访问其他人的主页」。核查后确认 —— **该功能此前不存在**：
全站只有 `/me`（只看自己），没有任何「点击姓名 → 看他的主页」的链接。

用户决定：做、同意字段取舍、**隐藏行程类信息**、姓名改成可点链接、必须登录。

### 一、字段白名单（本决策的核心）

| 字段 | 是否展示 | 依据 |
| --- | --- | --- |
| 姓名 | ✅ | [R-53](#d-32-组织称谓社团是性质协会是正式名称第-75-轮) 明确「成员之间可见真实姓名」 |
| 角色 | ✅ | 无敏感性 |
| **个人简介** | ✅ | 这正是它的用途（[D-35](#d-35-个人主页完善定位待办集中个人简介第-81-轮)） |
| **自评分** | ✅ | [D-24](#d-24-自评分可由用户随时自行修改) 要求约球时供他人参考 |
| 比赛积分 / 排名 / 战绩 | ✅ | 排行榜本就公开（[R-29](requirements.md)、[R-54](requirements.md)） |
| **学号** | ❌ | [R-53](requirements.md) 明确「学号不对任何成员展示」 |
| **QQ 号** | ❌ | 公开会让机器人账号被骚扰 —— 与手机号同级的敏感信息 |
| **我报名的活动 / 我发起的约球** | ❌ | **行程信息**。公开等于告诉所有人「我某天某时在哪」 |

**实现方式**：白名单落在一个服务函数里（`getPublicMember`），
**不查询、不返回**白名单外的字段 —— 而不是「查出来再在页面上不显示」。
这样即使将来页面写错，也不会泄露。

### 二、行程类信息为何必须隐藏

个人主页上的「我报名的活动」「我发起的约球」是**本人视角的待办**，
有明确用途（提醒自己）。但同一份数据搬到**别人的视角**就变成了行踪公开。

**同一条数据，在不同视角下的隐私含义完全不同** —— 这是本次最重要的判断。

### 三、必须登录

[R-53](requirements.md) 的措辞是「成员**之间**可见」，因此游客不应看到成员信息。
实测未登录访问 `/members/[id]` 返回 307 跳转登录页。

### 四、入口

姓名在以下位置改为可点链接（指向 `/members/[id]`）：排行榜、约球大厅发起人、
约球房间成员与申请人、活动页搭档、个人主页的待确认邀请。

为了把姓名链到主页，给两处数据结构补了 id 字段：`PendingInvite.partnerId`、
`getPartner()` 的返回值。**这两处原本只有姓名，是本次新增的能力。**

### 五、顺带修掉一个系统性的健壮性缺陷（缺陷不在本决策范围，但由它暴露）

**现象**：把 URL 里的 id 随便改成一个非 UUID 字符串，**8 个路由全部返回 500**。

**根因**：路径参数用户可控，最终传给 PostgreSQL 的 `uuid` 列。
字符串转 uuid 在**语法层面**就失败，抛 `invalid input syntax for type uuid`。
这**不是本次新引入的** —— 是长期存在的缺陷，只是做成员主页时才被测到。

**修法**：在 `lib/db.ts`（全项目**唯一的参数出口**）加一层参数处理 ——
从 SQL 文本解析出「与 uuid 列做等值比较」的参数位置，只对这些位置做校验，
非法值替换为哨兵 UUID（而非 null —— 数组参数换成 null 会引发新的报错）。

**为什么不逐个路由校验**：有 26 个带 `[id]` 的路由，逐个写必然遗漏。

**已知边界**：`INSERT ... VALUES ($1)` 里传给 uuid 列的参数识别不到。
可接受 —— 那些值来自已认证的用户 id，不是用户可控输入。

**教训**：一个安全/健壮性问题往往**不止一处**。发现一个 500 时，
应当系统性地扫描同类路由，而不是只修眼前那一个。

## D-37 NapCat 快速登录：一行环境变量解决「每次重启都要扫码」（第 96 轮）

**背景**：用户报告「机器人挂了」。排查过程见下，结论是一个**被误解了很久的现象**。

### 一、故障现象与排查

| 检查项 | 结果 |
| --- | --- |
| bot 容器 | ✅ 进程健康，WebSocket 监听正常 |
| 连接状态 | ❌ `16:29:57 协议端连接断开`，此后无重连 |
| NapCat | ❌ 每 2 分钟重试登录，全部失败：`Login Error, ErrType: 1 ErrCode: 3` |
| 容器重启次数 | `RestartCount=0` —— **容器从未重启**，是 QQ 会话自己在服务端失效 |
| NapCat 版本 | `4.18.37`，镜像两天前构建，**不旧** |
| 是否别处登录 | 用户确认**没有** |

**结论**：QQ 服务端单方面使该会话失效，**根因未能确定**（样本仅两次）。
用户扫码后恢复。

### 二、意外发现：重启要扫码的真正原因

排查中重启 NapCat 做验证，日志出现：

```
没有 -q 指令指定快速登录，将使用二维码登录方式
可用于快速登录 of QQ：          ← 凭据就在卷里！
```

**根因**：NapCat 的 `entrypoint.sh` 有两条分支 ——

```bash
if [ -n "${ACCOUNT}" ]; then  qq --no-sandbox -q $ACCOUNT   # 快速登录
else                          qq --no-sandbox              # 二维码登录
fi
```

**而 compose 从未设置 `ACCOUNT`**，因此每次启动都走二维码登录，
尽管快速登录凭据一直保存在 `napcat_qq` 卷中。

**修复**：`.env` 中设 `BOT_QQ=<机器人QQ号>`，compose 将其作为 `ACCOUNT` 传入。

**验证结果**：

| 指标 | 修复后 |
| --- | --- |
| 登录方式 | `正在快速登录  2864672917` |
| 二维码生成次数 | **0** |
| bot 重连 | ✅ 自动完成 |
| 是否需人工扫码 | **不需要** |

### 三、这个决策真正要记的是「教训」

**「每次重启 NapCat 都要重新扫码」此前被当作 NapCat 的固有行为，
写进了 README 的「必须知道的运维事项」，并据此形成了「改配置要攒着一起改」的运维习惯。**

**但它只是差一个环境变量。**

**为什么会被误记**：第一次遇到时，观察到「重启 → 需要扫码」这个相关性，
就直接当成了因果关系并归档；此后每次重启都验证了「确实要扫码」，
于是这个结论不断被「确认」，**却从未被质疑**。

**教训**：

> **把现象当成结论、不再追问原因，会让一个一行的修复被当成永久性的运维负担。**

自我印证的观察（每次重启都扫码）**不等于**因果解释（因为登录态不能持久化）。

### 四、修正一个概念混淆

排查过程中发现，**两件不同的事被混为一谈**：

| 现象 | 真正原因 | 状态 |
| --- | --- | --- |
| 每次重启要扫码 | 缺 `ACCOUNT` | ✅ 已修复 |
| 运行中突然掉线 | **QQ 服务端使会话失效** | ⚠️ 仍可能发生 |

后者才是真正需要人工介入的情况，且 **NapCat 没有离线消息队列** ——
掉线期间的消息**永久丢失**，不会补发。

### 五、附带改动

新增共享卷 `napcat_cache`（napcat 侧已挂载），
供 web 只读读取二维码文件 —— **这是「超管面板显示二维码」的前置条件**，
该面板本身尚未实现（用户要求「掉登录时二维码在超管面板刷新」）。

### 六、过程中我的一个测试失误

为做端到端验证，我向 `127.0.0.1:3001` 发 OneBot HTTP 请求 —— **端口错了**。
该 API 在容器内的 `3000`，而 compose 只映射了 `3001`（WebUI）与 `6099`。

**该自检方法不成立，但也不需要修**：那是 NapCat 的内部能力，网站与 bot 都没用它。
**记录在此以免下次又走同一条错路。**

## D-38 超管面板的机器人状态与登录二维码（第 99 轮）

**需求（用户提出）**：「如果掉登录，二维码在超级管理员的管理面板刷新」。

这个要求比原先设想的「临时开一个公开 /qr 路由」好得多 —— 后者任何人访问都能抢登。

### 一、状态从哪来

**唯一真相源是 bot 与 NapCat 之间 WebSocket 的连接状态。**
网站无法自行判断（两个独立容器），因此由 bot 上报。

**先修掉一个「假健康检查」**：bot 原先的 `/healthz` **永远返回 200**，
即使 NapCat 早已断开 —— 这正是机器人停摆近 4 小时无人察觉的原因。
现改为：未连接时返回 **503**（Docker 会把容器标记为 unhealthy），并新增 `/status` 返回 `{connected}`。

**连接状态的维护**：在连接处理里用 `try/finally` 设置，**任何退出路径都置回未连接** ——
否则状态会停在「已连接」，健康检查又变成假的。

### 二、二维码怎么拿到

NapCat 等待扫码时会持续把二维码写到 `/app/napcat/cache/qrcode.png`，
因此新增共享卷 `napcat_cache`，**以只读方式**挂给 web（web 只需读取）。

**登录态无法直接查询，只能旁证**：
「未连接 + 二维码文件是新的（5 分钟内）」基本可断定是掉登录、且现在就能扫。

### 三、权限：仅超级管理员

| 层 | 措施 |
| --- | --- |
| 后台卡片 | 仅 super_admin 可见（实测普通管理员看到 **0** 次） |
| 二维码接口 | 仅超管；未登录 **401**、普通管理员 **403**（均实测） |
| 只读挂载 | web 容器无法篡改二维码文件 |
| 响应头 | `Cache-Control: no-store` —— 缓存旧码会让人扫到已失效的二维码 |

**关于「超管能看到二维码 = 能登录机器人」是否越权**：
超管本来就能重置任意成员密码、设置管理员、删任何内容。
在这个权限模型下，能看到二维码**并不越权**，而且「恢复通道」本就该放在最高权限处。

### 四、必须自动刷新

NapCat 的二维码**约 2 分钟失效**。若页面只加载一次，超管打开面板时看到的
很可能是已过期的码 —— 扫了没反应，还以为是坏了。
因此客户端每 **30 秒**重新拉取，并带查询参数绕过缓存（服务端 `no-store` 为双保险）。

### 五、面板的四种状态

| 状态 | 显示 |
| --- | --- |
| 已连接 | 「运行中」—— **不显示二维码**（正常运行时不占版面） |
| 未连接 + 有新鲜二维码 | 「需要重新扫码」+ 实时二维码 |
| 未连接 + 无二维码 | 提示在服务器执行 `docker compose restart napcat` |
| 连不上 bot 本身 | 提示检查 bot 容器 |

### 六、⚠️ 排障中发现的一个静默失败（比本功能更严重）

**现象**：bot 的新代码部署后不生效，`/status` 一直 404。

**根因**：`docker-compose.yml` 里 **bot 服务只有 `build:` 而没有 `image:`**。
此时 compose 自行生成镜像名（`nefu-pa-web-bot`），
与部署流程中 `docker build -t nefu-pa-web-bot:local` 构建的名字**对不上**。
后果：`docker compose up -d --force-recreate bot` **继续复用上一次的旧镜像**，
**不报任何错** —— 属于静默失败。

**web 服务早已显式写了 `image:`，因此没有这个问题。**
这也解释了为什么之前几次 bot 代码改动「部署了」却像是没生效。

**修复**：为 bot 补上 `image: nefu-pa-web-bot:local`。

**教训**：这与第 78 轮那次「构建失败后仍继续部署旧镜像」是**同一类问题** ——
**部署流程的静默失败**。两次都不是代码写错，而是「以为部署了，其实没有」。
部署后应当**验证运行中的究竟是不是新版本**（本次是靠 `/status` 返回 404 才发现的）。

### 七、未能验证的部分（如实记录）

**「掉线并显示二维码」这条分支没有实测过。**
要触发它必须真的让 NapCat 掉登录，而那会影响正在使用机器人的成员。
已验证的是：状态上报正确、权限边界正确、「运行中」分支正确、
接口在已连接时正确返回 404（不泄露二维码）。

**该分支的代码逻辑已审阅，但「实测通过」这四个字不能写。**

## D-39 「是否参与排行」开关：自愿退出排行榜（第 100 轮）

**需求（用户提出）**：个人主页加一个开关，关闭后**暂时退出排行榜**，可随时恢复。

### 一、与 D-30「不设场次门槛」的关系

[D-30](#d-30-积分模块的三项收尾决定第-61-轮) 定的是「**不设门槛**，但榜上显示场次」，
理由是设门槛会把新成员挡在榜外。

**本决策与它不冲突**：那是**系统单方面**的限制，这是**用户自愿**的选择。
两者方向相反但依据相同 —— 都尊重「成员自己愿不愿意被比较」。

### 二、核心设计：隐藏者**整个从排名计算中剔除**

| 方案 | 效果 | 是否采用 |
| --- | --- | --- |
| **整个剔除** | 榜上第 N 名 = 可见者中的第 N 名 | ✅ |
| 占位但显示「已隐藏」 | 榜单出现读者无法解释的空洞 | ❌ |

**实测验证**：8 人榜、自己在第 7 名 → 关闭后榜上 **7 人**、自己消失；
恢复后回到 **8 人、第 7 名**。

### 三、不影响积分，因此对其他人完全公平

关闭后：

| 项目 | 是否受影响 |
| --- | --- |
| 比赛积分 | ❌ **照常累积** |
| 能否参加比赛 | ❌ 不受影响 |
| 其他人的积分结算 | ❌ 不受影响（他们仍在与隐藏者对战） |
| 是否出现在榜上 | ✅ **仅此一项** |

**这一点必须在界面上写清楚**，否则用户会以为「退出排行 = 不玩了」。

### 四、按**赛季**存储，不是按账号

字段放在 `season_ratings.leaderboard_hidden` 而不是 `users` 上：
「上个赛季不想上榜、这个赛季想上榜」是很自然的事，
放在 `users` 会导致**一次关闭就永久生效**。

### 五、实现要点：过滤条件必须一致

**所有**涉及排名的查询都要带 `NOT leaderboard_hidden`，否则会出现自相矛盾的显示：

| 位置 | 若漏掉的后果 |
| --- | --- |
| 榜单行 | 隐藏者仍然可见（功能失效） |
| 榜单总数 | 「共 8 人」但只列出 7 个 |
| `getMyRank` | 自己看到「第 3 名」但榜上找不到自己 |
| 个人主页的总人数 | 「我第 3 / 共 8 人」而榜单只有 7 人 |

**其中「个人主页的总人数」是排查时发现并一并修正的** ——
它原本没带过滤条件，属于本次改动**顺带暴露**的既有不一致。

### 六、没有加操作记录

与 D-35 的个人简介同理：这是**用户对自己可见性的选择**，
不影响他人权益，留痕只会淹没真正重要的记录。

### 七、顺带确认的一件事

排查时发现「今天注册的 5 位新成员还没打过比赛就有积分记录」，
一度怀疑是异常。核实后确认是**既有设计**：注册时即建立本赛季积分记录，
初始 500（[D-09](#d-09-积分算法标准-elo)），字段默认值本就是 500 —— 所有成员从同一起跑线开始。
而 `leaderboard_hidden` 默认 false，因此他们都能正常使用本开关。

## D-40 NapCat 看门狗：被踢下线后自动恢复（第 103 轮）

**背景**：用户报告「周期性掉线」。排查确认了**两个不同的问题叠加**。

### 一、故障链

```
QQ 服务端主动踢下线（日志：KickedOffLine [下线通知] 你的账号当前登录已失效）
    ↓
NapCat 在**容器内部**重启进程
    ↓
但 entrypoint 不会重跑 → 启动参数 -q <QQ号>（快速登录）丢失
    ↓
NapCat 退化成二维码登录、卡住等人扫
    ↓
无人察觉，实测停摆可达数小时
```

**关键区别**（D-37 修复的是另一件事）：

| 重启方式 | entrypoint 是否重跑 | 能否自动快速登录 |
| --- | --- | --- |
| **整个容器重启** | ✅ 会 | ✅ 能（D-37 已验证） |
| **NapCat 内部重启** | ❌ 不会 | ❌ 不能，只能扫码 |

### 二、为什么被踢 —— **未能确定**

已排除的原因（均有证据）：

| 假设 | 排除依据 |
| --- | --- |
| 别处登录挤下线 | 用户确认没有 |
| 多实例冲突 | 只有一个 QQ 进程（`ps` 确认） |
| 另一个机器人占用同号 | LLBot 用的是 `3641000342`，与本项目 `2864672917` 不同 |
| 容器崩溃 | `RestartCount=0` |
| 定时任务 | 两次被踢间隔不一致（1h57m 与 28m） |

**最可能是 QQ 服务端对自动化客户端的安全策略，但没有证据，因此不写结论。**

### 三、看门狗：只解决「恢复」，不假装解决「原因」

「为什么被踢」不受我们控制，但「被踢后要人工扫码」可以解决。

**做法**：`scripts/napcat_watchdog.py` 每 2 分钟检查一次；
发现「未连接 + 日志里有 KickedOffLine」时，重启 napcat 容器 ——
容器重启让 entrypoint 重跑，`-q` 参数恢复，于是自动快速登录。

**效果**：掉线时间从「数小时（等人发现）」缩短到 **约 1 分钟**。

### 四、防循环：这是必须有的安全阀

若登录态是**真失效**（不是被踢），重启也登不上，就会无限重启。

| 保护 | 作用 |
| --- | --- |
| **冷却窗口 30 分钟** | 窗口内只尝试一次 |
| **只在 KickedOffLine 时动手** | 容器正在启动等正常情况不打断 |
| **状态写文件** | 超管面板显示「已尝试自动恢复但未成功」，并直接给出二维码 |

**面板是这个方案的安全网** —— 自动恢复失败时，管理者无需登录服务器即可扫码。

### 五、实测

用桩函数模拟五种路径，全部符合预期：

| 场景 | 期望 | 结果 |
| --- | --- | --- |
| 未连接 + 被踢 + 无历史 | 触发重启 | ✅ |
| 刚尝试过（60 秒前） | 冷却跳过 | ✅ |
| 冷却已过（31 分钟前） | 允许再次尝试 | ✅ |
| 未连接但没被踢 | 不动手 | ✅ |
| 已连接 | 清理告警痕迹 | ✅ |

**未实测**：真实被踢时的端到端恢复（需要 QQ 真的踢一次）。

### 六、需要用户执行的一步

安装 systemd 定时器**需要 sudo**，维护者无法代做：

```bash
sudo cp ~/nefu-pa-web/deploy/napcat-watchdog.{service,timer} /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now napcat-watchdog.timer
```

**在此之前看门狗不会自动运行**（脚本与配置已就位，只差这一步）。

## D-41 机器人回复文案可自定义（第 106 轮）

**需求（用户提出）**：机器人回复内容可否自定义。用户决定：**A+B 全部放开**、
**支持占位符**、**改完不需要重启机器人**。

### 一、范围：9 条文案全部可改

原先 10 条回复**全部写死在 `handlers.py` 里**。现在改为模板 + 占位符：

| 分组 | 文案 |
| --- | --- |
| **主流程** | 注册回复、重置密码提示、重置成功 |
| **边界提示** | 已注册、未注册、密码太短、注册失败、重置失败、不认识的指令 |

**关于边界提示的风险**：它们原本是**规则的一部分**（比如「密码至少 6 位」）。
放开自定义意味着管理员可能改错、导致用户困惑。
**但这是用户明确的选择**，因此按「用占位符强制保留关键信息」的方式实现，而不是禁止修改。

### 二、占位符：安全阀，不是可选项

| 占位符 | 含义 |
| --- | --- |
| `{code}` | 邀请码 |
| `{url}` | 网站地址 |
| `{minPassword}` | 密码最小长度 |

**保存时强制校验**：

| 校验 | 拦截的问题 |
| --- | --- |
| 必填占位符必须存在 | 管理员删掉 `{code}` → **机器人再也发不出邀请码**，且不报错、极难排查 |
| 不允许未知占位符 | 写成 `{cod}` 会**原样出现在用户看到的回复里** |

**实测三条拦截**（均返回明确错误）：

```
删掉 {code}        → 必须包含占位符 {code} —— 否则这条回复会缺少关键信息
用未知的 {cod}     → 含有未知的占位符 {cod}。可用的是：{code}、{url}、{minPassword}
漏掉 {minPassword} → 必须包含占位符 {minPassword} —— 否则这条回复会缺少关键信息
```

### 三、存储：复用 site_settings，不新建表

运维文案存进 [D-34](#d-34-首页文案可编辑用键值配置表而不是每项一张表第-80-轮) 的键值表，
**因此这次改动没有迁移**。

同时把保存逻辑抽成 `modules/setting/save.ts` 供两页共用 ——
若各写一份，校验规则迟早漂移（一处限制了长度、另一处忘了）。

### 四、谁能改

**管理员及以上**（与首页文案同级）。
文案是面向全体成员的对外内容，属「发布」类能力。

### 五、免重启：靠 TTL 缓存

机器人每次回复前取文案，**带 60 秒 TTL 缓存**：

| 设计 | 理由 |
| --- | --- |
| 缓存 60 秒 | 每条消息都请求网站会给 web 无谓压力；60 秒延迟对「改完想立刻看效果」足够 |
| **不需要重启** | 这正是需求要求的 |
| 取不到时用**内置兜底** | **网站挂了不能连机器人一起变哑巴** |

**兜底文案与网站默认值有意重复** —— 这是有意的取舍：
重复换来了「网站不可用时机器人仍能工作」。

### 六、文案住在网站侧

机器人经共享规则接口的 `get-bot-messages` 取模板，
**不自己存一份** —— 与密码加密同理：规则只实现一份，否则两边必然漂移。

返回的是**模板**（含占位符），由机器人填值，因为只有它知道 `SITE_URL`。

### 七、实测

| 项 | 结果 |
| --- | --- |
| 管理页 9 个字段 | ✅ |
| 接口返回 9 个模板、含 `{code}` | ✅ |
| 填占位符后的实际回复 | ✅ 邀请码与地址正确 |
| 三条危险操作拦截 | ✅ |
| **改完 65 秒后机器人已用新文案** | ✅ **免重启验证通过** |

## D-42 放弃迁移官方 QQ 机器人平台（第 114 轮）

**背景**：NapCat 属第三方协议端，存在封号风险且近期反复掉线。
用户提出「第三方框架还是有点不稳，查询一下官方 bot 框架的可用性」。

**调查结论**：官方平台**能力限制过紧，不可行**（用户实测后确认）。

### 一、调查得到的硬约束（有据可查）

| 约束 | 内容 | 对本项目的影响 |
| --- | --- | --- |
| **主动消息已停用** | 2025-04-21 起不再提供，接口调用报错 | 影响小 —— 本项目本就[不做通知推送](#d-14-不做-qq-通知推送) |
| **被动回复额度** | 单聊：一条消息 60 分钟内最多回 5 条 | 注册流程 1 条够用；重置流程 3 条接近上限 |
| **内容含 URL 需预配置** | 否则发送失败 | 注册回复里的注册链接需要额外后台配置 |
| **身份是 openid** | 不是真实 QQ 号，且用户自己不知道 | **最大障碍** —— 现有 [D-01](#d-01-身份与准入) 以真实 QQ 号为锚点，需整体改造 |
| **上线需审核** | 沙箱仅对平台内添加的测试用户开放 | 「能否上线」不完全由自己控制 |

### 二、决定：不迁移，继续用 NapCat

**理由**：官方平台的收益（零封号风险）不足以抵偿改造代价与能力约束。

**这意味着接受第三方协议端的固有风险**，包括：

- 账号可能被封（规划期已评估接受，见 [scope.md](scope.md) 风险 R8）
- 服务端可能随时使会话失效（本期已多次发生）

### 三、既然不迁移，「不稳」要靠工程手段兜

官方路线堵死后，方向转为**把 NapCat 的不可靠性隔离在运维层**。
已有的两层防护（本轮之前完成）：

| 层次 | 机制 | 状态 |
| --- | --- | --- |
| **自动恢复** | 看门狗检测被踢 → 重启容器恢复快速登录 | ✅ [D-40](#d-40-napcat-看门狗被踢下线后自动恢复第-103-轮) |
| **人工兜底** | 超管面板显示实时二维码 | ✅ [D-38](#d-38-超管面板的机器人状态与登录二维码第-99-轮) |

**实测有效性**：

- 08:29 被踢 → 看门狗 **1 分 42 秒**内自动重启并发起快速登录 ✅
- 08:31 快速登录因**凭据失效**失败 → 超管面板即刻显示二维码，用户扫码恢复 ✅

**也就是说：两层防护都实际用过一次，都起作用了。**
真正未被覆盖的只剩「凭据失效」这一类 —— 而它**本质上必须人工扫码**，
任何自动方案都救不了（官方平台同样需要重新授权）。

### 四、尚未处理的改进点

| 问题 | 说明 |
| --- | --- |
| **NapCat 停止生成二维码** | 本期出现过：二维码停在某一时刻不再更新，用户扫的一直是死码。当前只能靠人工重启 |
| 掉线期间消息永久丢失 | NapCat 无离线队列，属协议端固有限制，无法解决 |

第一条已记录，是否处理待用户决定。

## D-43 站内消息通知（第 141 轮）

**背景**：约球被申请、申请被审批、被设为管理员等事件，当事人原本无从知晓 ——
只能靠自己反复刷新页面碰运气。用户提出「新增站内消息通知」。

**决策：只做站内通知，不接机器人。**

### 一、为什么不经 QQ 推送（关键取舍）

技术上完全可行（`send_private_msg` 现成可用），但**主动私聊是账号风控的高危行为**：

| 依据 | 说明 |
| --- | --- |
| 本项目实测经历 | 机器人账号曾因风控被限制（`state=168 社交功能限制`） |
| [D-14](#d-14-不做-qq-通知推送) | 此前已明确拒绝主动推送 |
| 连带风险 | 被通知的是**成员的个人 QQ 号**，机器人若被判定为垃圾信息源可能连累成员 |

**并且**：即使要做，也有更安全的中间形态 —— 用户**主动**给机器人发指令时
顺带回复未读通知（纯被动、零风险）。本期不做，但方案已记录，将来若需要从这里起步。

### 二、数据模型

`notifications` 表（迁移 018）。两个设计要点：

1. **文案在写入时定稿**（存 title/body 而非 payload）。通知是**事件的快照**，
   「当时通知了什么」就该保持不变；否则历史通知会随之后改名/改文案而变样。
   这与审计日志同思路。
2. **未读计数走部分索引**（`WHERE read_at IS NULL`）。红点在每次页面渲染时都要查，
   值得让它更小更快。

另有 `dedupe_key`：同一用户、同一键、30 分钟内只留一条。
用于「一个约球被多人连着申请」这类会来一串的事件，避免刷屏。

### 三、事件清单（首批）

| kind | 通知谁 | 触发点 |
| --- | --- | --- |
| `room.applied` | 发起人 | 有人申请（带去重） |
| `room.decided` | 申请人 | 通过 / 拒绝 |
| `room.withdrawn` | 发起人 | 已加入者退出 |
| `room.cancelled` | 全部已加入者 | 发起人取消房间 |
| `event.promoted` | 候补者 | **自动递补为正式报名** |
| `event.released` | 搭档 | 队友取消导致整队释放（D-28） |
| `role.changed` | 当事人 | 被设为 / 取消管理员（仅角色真的变了才发） |

**`event.promoted` 尤其要紧**：候补的人不知道自己已被递补，就不会来。

### 四、实现约束

**通知在事务提交之后发，且失败不影响主流程**（`record()` 内部吞异常）——
与审计模块同一原则：若通知失败导致「审批约球」失败，那是本末倒置。

为此 `room/service.ts` 与 `event/service.ts` 的几个函数拆成了「事务部分 + 外层通知」，
事务部分多返回发通知所需的信息（申请人 id、房间时间段、活动名等）。

### 五、界面

* **导航栏**：有未读时，用户名旁亮红点，且「我的」直接指向消息页 ——
  红点与它的入口是同一个东西，不做成只能看不能点的装饰。
* **个人中心**：独立的「消息」入口（带未读数）。
* `/notifications`：列表、未读高亮、点击即已读并跳转、全部标为已读。

### 六、实施中发现并修掉的两个问题

1. **`new URL(path, req.url)` 会跳到容器内地址**。
   `/api/notifications/read` 是项目里第一条用 `NextResponse.redirect` 的路由，
   实测跳转目标是 `http://0.0.0.0:3000/...`（应用监听地址）—— 用户会打不开。
   改为用 Caddy 传来的 `x-forwarded-host` / `x-forwarded-proto` 拼绝对地址。
2. **`to` 参数的开放重定向防护**：只放行站内路径（单个 `/` 开头、非 `//`），
   并额外拒绝反斜杠 —— 部分浏览器把 `\` 当 `/`，`\/\/evil.com` 能绕过字符串检查。

### 七、验证方式

建临时测试账号走完整流程（申请约球 → 发起人收到通知 → 红点 → 列表 → 已读），
并测了开放重定向的四种绕过尝试，**测完删除全部测试数据**（用户数回到 14、通知 0）。

## D-44 约球改为「活动结束后过期」，时间改用真实时间戳（第 145 轮）

**背景**：用户提出「把约球设计成不录入成绩的、由成员发起的活动」。
评估后认为该定位准确（与 D-10、D-04 一致，无需改模型），但**暴露了一个真实缺陷**。

### 一、原规则的问题

```sql
expires_at = now() + 24 hours   -- 从「发布时刻」起算
```

**后果**：想组织「下周六打球」，今天发布 → 明天就被标记过期、从大厅消失，
只能等到临近才能发。**成员办活动通常要提前几天通知**，
这条规则其实只适合「今天找搭子」。

### 二、改法

| | 原来 | 现在 |
| --- | --- | --- |
| 时间字段 | `time_slot text`（如「周六 14:00-16:00」） | `start_at timestamptz NOT NULL` + `end_at timestamptz`（选填） |
| 过期时间 | 发布 + 24 小时 | **活动结束后 2 小时**（无结束时间则开始后 4 小时） |
| 列表排序 | 创建时间倒序 | **活动开始时间升序**（最近要打的排最前） |

**副作用是好的**：时间已过的房间会**自动下架**，
而原来它要等满 24 小时才消失。

结束时间选填 —— 大多数约球说不准打到几点。

### 三、连带修掉一个**全站性**的时区 bug

实施中发现 web 容器**没有设 `TZ`**，进程时区是 UTC。

| 后果 | 说明 |
| --- | --- |
| 所有时间显示差 8 小时 | 全站用 `toLocaleString("zh-CN")`，它依赖进程时区 |
| **datetime-local 输入被当成 UTC** | `new Date("2026-10-20T15:00")` 解析为 15:00Z，成员填「15:00」实际存成「23:00」 |

**第二条尤其隐蔽**：表单看着对、数据库里全错 8 小时，页面再渲染出来又变回 15:00。
房间模块实测确诊（提交 15:00 → 存储 23:00）。
加 `TZ: Asia/Shanghai` 后两条一起解决。

> 注：`events` 模块的创建表单可能存在**同一类**输入问题（把 datetime-local 当 UTC 解析），
> 本次未动（用户只要求改约球）。**已有活动的时间可能偏 8 小时**，需另行确认。

### 四、存量数据迁移（三个迁移，逐个踩坑）

| 迁移 | 做了什么 |
| --- | --- |
| `019` | 清理 cancelled；加 start_at/end_at；按人工确认的日期写入存量数据 |
| `020` | **修正 019 没匹配上的两行** |
| `021` | 修复「未到期却标记过期」的状态不一致 |

**019 的教训**：它用 `WHERE time_slot = '周二15:00-17:00'` 精确匹配人工输入的文本，
**一行都没匹配上**（文本含不可见差异），于是落到兜底分支 `created_at + 1 day`，
时间全错 8 小时。**迁移里不要按人工输入的文本做精确匹配。**

**021 的教训**：`expireDue()` 是**单向标记**（只把 open/full 变成 expired，不会变回来）。
时间被修正后，先前误标的房间不会自动恢复 —— 需要显式对账。

### 五、未做的部分（用户明确只要求 A）

| 项 | 状态 |
| --- | --- |
| 加场地字段 | 未做（活动有 `location`，约球仍只能写备注） |
| 改名为「成员活动」 | 未做 |
| 加入方式改为「自动 + 候补」 | 未做，且**不建议** —— D-10 已明确选择发起人审批制 |
| 成员发起**计分**比赛 | 未做。技术上只需一个开关，但计分是零和的，成员自组织比赛计入积分**可能引发争议** |

## D-45 注册与重置密码改为「群内 @ 确认」（第 165-177 轮）

**背景**：机器人**非好友私聊**是腾讯风控的高危模式（陌生人私聊骚扰的典型特征）。
而原注册流程要求成员先私聊机器人领邀请码，于是**每次注册都产生一次陌生私聊**。
用户提出把注册流程转移到群聊。

### 一、核心矛盾与解法

**「搬到群里」不能简单地把邀请码发到群里** —— 那等于公开凭据，
而且机器人在群里，别的机器人也能读到。

因此改掉的不是一个位置，而是**整个准入机制**：

| | 旧 | 新 |
| --- | --- | --- |
| 准入依据 | 邀请码（一码绑一 QQ，永久有效） | **QQ 号在群成员列表中** |
| 确认方式 | 私聊机器人发「注册」拿码 | **机器人群里 @ 本人 → 本人回复确认** |
| 私聊 | **必需** | **完全不需要**（私聊已停用） |

**关键安全依据是「双向匹配」**，两点缺一不可：

1. 机器人 @ 的是**目标本人**；
2. bot **只认发言者的 QQ 号**（消息文本里写的号码一律不信）。

**攻击者无法用别人的号在群里发言，因此无法代他人确认。**

### 二、两条流程

```
注册：网站填表（姓名/学号/密码/QQ号）→ 机器人群里 @ 本人
      → 本人回复「确认注册」→ 建号 → 网站轮询到 → 自动登录

重置：网站填 QQ 号 → 机器人群里 @ 本人 → 本人回复「确认重置」
      → **回到发起重置的那个浏览器**就地设置新密码
```

### 三、重置密码为什么是「同浏览器完成」而不是「私聊发链接」

最初设计是私聊发一次性改密链接，但存在一个真实缺陷：

> **「谁发起」与「谁确认」可能是两个人。**
> 攻击者可以发起重置，再诱导被 @ 的人「看到提醒就顺手回复确认」，
> 于是改密凭据落到攻击者能诱导到的位置。

改为「同浏览器完成」后，改密**额外要求带着发起时下发的 httpOnly cookie**：

| 校验 | 证明什么 |
| --- | --- |
| 群里已确认 | **QQ 号所有权** |
| 带着发起时的 cookie | **同一个浏览器** |

**攻击者即便诱导受害者确认成功，也拿不到受害者浏览器里的 cookie，因此改不了密码。**
顺带的好处：**彻底不需要私聊** —— 机器人不必主动联系任何人。

### 四、残余风险与缓解

| 风险 | 缓解 |
| --- | --- |
| **QQ 号被冒用**（填别人的号发起） | @ 的是真实号主；他能看到并**选择不回复**；10 分钟自动过期 |
| **社交工程**（诱导号主回复确认） | @ 文案明确写「**如果不是你，请忽略**」；确认词用「确认重置」而非泛泛的「确认」；**加上同浏览器绑定后此路径已基本失效** |
| **群里 @ 刷屏** | 同一 QQ 号 5 分钟节流；表上唯一约束使重复发起**覆盖**而非追加 |

### 五、数据模型

新增两张表（迁移 022，024 补列）：

- `pending_registrations` —— 待确认注册，含 `password_hash`。
  **这是「必要的恶」**：确认发生在另一个请求里，密码必须活到那时。
  缓解：10 分钟 TTL、确认后随记录删除、与正式密码同一套 scrypt。
- `pending_password_resets` —— 待确认重置，含 `initiator_hash`（发起凭据的 sha256）。
  **明文只存在于发起者的 httpOnly cookie 里，绝不进群、绝不入库。**

### 六、实施中踩到并修掉的坑

| # | 问题 | 说明 |
| --- | --- | --- |
| 1 | **`SELECT … FOR UPDATE` 需要 UPDATE 权限** | 迁移 022 只授了 SELECT/INSERT/DELETE，确认注册时直接报 `permission denied`。**教训：授权要按「会执行的操作」推，不是按「会读写的表」推** —— 行锁这类隐式要求最容易漏（迁移 023） |
| 2 | 缺 `seasons` / `login_sessions` 权限 | 建积分、踢旧会话时才会暴露，被 #1 掩盖了 |
| 3 | **`new URL(path, request.url)` 跳到容器内地址** | 把握手后的用户送到 `http://0.0.0.0:3000`。项目里已有 `redirectTo()` 辅助函数专门解决，但写新路由时又忘了用它 |
| 4 | **全站 3 处旧引导未同步** | 首页、登录页、忘记密码页仍在教用户「私聊机器人」，而私聊已停用 —— **用户照做不会有任何反应**。教训：改机制时必须同步清理「告诉用户怎么做」的地方 |

### 七、邀请码的去留

`invite_codes` 表**保留**（数据留档），但不再读写；
`/api/internal/shared-rules` 的 `generate-invite-code` 也保留（避免破坏接口）。
bot 侧生成邀请码的代码路径已不再被调用。

### 八、顺带的改进

- **社团 QQ 群号改为后台可配置**（`/admin/home`），换群不必改代码。
- 后台首页设置页的 `maxLength` 改用各字段自己的上限（原为写死 200/40）。
- `db/schema.sql` 补齐了迁移 010/012/018/022 新增的 5 张表 ——
  这份「首次建库用」的权威 schema 此前落后了四个迁移，会误导读它的人。
  （已在临时库上验证可完整建库，21 张表。）
